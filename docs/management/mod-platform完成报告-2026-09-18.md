## 二、P0 交付（4 条 + 2 个自查回归）

### 1. 密钥轮换不再丢数据
**原缺陷**：`rotate_key()` 只写新的 key_file，历史密文全部作废——轮换即是
数据自杀，且当时没有任何提示。

**修复**：新增 `SecurityService.rotate_key()`：
```
先解密全部密文（vault_items.secret_encrypted + settings 密文）
  → 换 key
  → 用新密钥逐条重加密写回
任一步失败 → 整体回滚，不留"半新半旧"的库
```
端点 `/security/key/rotate` 改为走该服务。

### 2. 加解密端点门禁
**原缺陷**：`/security/encrypt|decrypt|key/rotate` 无任何前置校验——
任何能触达 API 的调用（含被注入的前端脚本）都可批量解密用户密钥。

**修复**：三端点要求**保险箱处于解锁态**（`require_unlocked`），未解锁
返回明确业务错误。与 server.js 的访问令牌形成两层：外网进不来、进来了
也解不开。

### 3. 同步删除传导
**原缺陷**：diff 只增不删——你在手机上删掉的任务，PC 上永远留着。

**修复**：`diff(propagate_deletes=False)`：
- **默认关闭**（远端包可能是裁剪过的，开启会误删本地数据）
- 开启后：本地有而远端无 → 落**墓碑软删**（写 `deleted_at`，不硬删，
  保留同步所需的墓碑语义）
- 双重防御：**对端未给出某张表时绝不删**（空 dict = 不掌握情况）

### 4. 禁止明文降级
**原缺陷**：`encrypt_secret` 在 DPAPI 不可用时返回 `plain:` + base64 ——
等于明文落库。

**修复**：三级后端 —— `DPAPI` → `Fernet`（真加密，文件密钥）→ **仅开发
模式**的 `plain:` 占位 → 生产环境直接拒绝写入并抛明确异常。
`decrypt_secret` 同步支持 `fernet:` 前缀，保留 `plain:` 历史兼容读取。

### 5–6. 自查发现的两个回归（本轮新增）
- **`init_encryption` 全项目无调用点** → `get_encryption()` 恒为 None，
  Fernet 回退形同虚设、生产保存 API Key 直接抛错。**修复**：lifespan
  启动时统一初始化。
- **`pywin32` 未安装** → DPAPI 不可用是常态，必须依赖 Fernet 回退。
  已在代码中体现（三级后端），并验证环境：`cryptography` 可用 ✅

## 三、P1 交付（5 项）

| 项 | 内容 | 关键设计 |
|---|---|---|
| 插件权限真正执行（F3.1） | 白名单 `network`/`db_read`/`files`；未知权限**拒绝加载**（fail-closed）；`exec`/`db_write`/`subprocess` 声明即拒绝；`has_permission()` 供运行时校验 | 单进程内无法真隔离 → 高危权限直接不放行 |
| 同步冲突预览（F2.4） | `SyncEngine.preview()` + `POST /sync/preview`：只算不改库，返回 total/by_op/by_table/前 8 条样例 | 导入前可判断"值不值得导"，避免盲 apply |
| 安全审计日志（F5.4） | `audit_logs` 表（迁移 0019，幂等守卫）+ 14 种动作白名单 + 加解密/轮换埋点（**成败都记**）+ `GET /security/audit` | `audit()` 自身永不抛异常——记日志不能打断业务 |
| 插件错误隔离（F3.4） | `safe_call()`：异常全捕获留痕 + 可超时（initialize 10s / shutdown 5s） | 超时必须 `pool.shutdown(wait=False)`——用 `with` 会 join 线程等于没超时（已写入注释防回归） |
| 加密管理器启动初始化 | lifespan 中 `init_encryption(data_dir)` | 全局单例真正可用，vault/assistant 不再各自 new |

## 五、诚实边界（未做及原因）

| 项 | 为什么先不做 |
|---|---|
| 同步增量（F2.1） | 当前数据量（千行级）全量 snapshot 仅 146ms，无痛点；数据量上万再启 |
| 字段级合并（O5） | 行级 LWW 在单人多设备场景冲突概率低；实现成本高 |
| 配置双写统一（O4） | localStorage 与 settings 表并存是历史设计，改动面大 |
| 规则引擎可配置（O6） | 偏产品功能，非底座问题 |
| 备份自动化（O7） | 实用但独立，可单开小分支 |
| 插件前端注册（O8）/ 设置搜索（O9） | P2 远期 |

## 六、给后续模块的复用资产

1. `safe_call()` —— 任何"调用外部不可信代码"的地方都可复用
2. `audit()` + `AUDIT_ACTIONS` —— 新增敏感动作只需登记动作名并埋点
3. 权限白名单模式 —— 其他模块做"能力授权"时可照搬
4. `propagate_deletes` 的**默认关闭 + 双防御**设计范式 —— 破坏性操作
   默认关、显式开、且要有兜底条件
