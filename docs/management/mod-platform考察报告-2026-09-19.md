## 三、考察发现的问题（3 项，已全部修复）

### 问题 1：新表未登记同步策略（数据卫生）
**现象**：`audit_logs`、`settings_history` 未出现在 `SYNC_POLICY`，`policy_of()` 默认返回
`FULL` → 审计日志与设置变更历史会**随同步包跨设备传播**。

**影响**：语义错误（"这台机器上发生过什么"不该跨端），且让同步包无谓膨胀。

**修复**：两张表登记为 `DERIVED_SKIP`，并加断言（策略非 FULL + snapshot 中不出现）。

### 问题 2：有一条永真断言在充数（自查打脸）
**现象**：`check("rules domains endpoint lists builtin+user", r.status_code in (405, 404) or True, "")`
—— `or True` 使其**永远通过**。

**影响**：污染"通过数"统计，是验证体系里的水分。

**修复**：删除。修复后有效断言净增（删 1 条假 + 加 7 条真）。

### 问题 3：`user.api_key_encrypted` 不在密钥轮换范围（**会真实丢数据**）
**现象**：`_CIPHER_COLUMNS` 只有 `vault_items.secret_encrypted`，而 AI API Key 密文存在
`users.api_key_encrypted`。密钥环（current + previous）**只保留两级密钥**——
第一次轮换靠 previous 兜底还能解密，**第二次轮换后更早的密钥被覆盖，该密文永久解不开**。

**影响**：高危。用户轮换两次主密码后，AI Key 静默失效且无法恢复。

**修复**：
- `_CIPHER_COLUMNS` 增加 `("users", "api_key_encrypted")`
- 收集阶段跳过 `dpapi:` 前缀密文（DPAPI 密钥由系统管理，不归本密钥环）
- 断言：轮换后 API Key 仍可解密（真实往返测试），且轮换端点返回 rotated 数

## 四、我对自己工作的评价（不护短）

**做得好的**
1. **验收标准转断言**——PRD §8 的检查项变成可执行断言，这是本模块最有价值的产出
2. **密钥环设计**——从"会丢数据"到"中断也不丢"，且断言锁死
3. **诚实标注边界**——2 项未测（1000 行导入回滚、设置页首屏）如实写在报告里，没有含糊过去

**需要改进的**
1. **自述数字不核对**：提交信息写"219 通过"实际 216。数字类陈述必须先跑再看
2. **新表缺"策略登记"意识**：建表时想到 `updated_at/deleted_at`，却漏了 `SYNC_POLICY`——
   说明"新增模型检查清单"还不完整，**应补进项目铁律**
3. **断言质量参差**：为了凑"确认某端点不存在"写了一条永真断言，属于自己给自己注水
4. **加密列清单靠人工维护**：`_CIPHER_COLUMNS` 是硬编码列表，加新加密列时容易再漏——
   建议后续做"加密列注册"机制（或用命名约定 + 架构守护校验）
