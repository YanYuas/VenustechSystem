## 二、根因诊断：为什么你会觉得乱

### 2.1 直接原因：系统只有一个分类轴

启明星目前的组织方式是**单线的**：任务 / 项目 / 文档 / 复盘各自成列，
彼此之间靠「文件夹」或「手动标签」勉强关联。

而你的实际结构是**多线的**。`D:\YanYuas` 下至少有 9 重身份在并行：

> AI 研究 · 数学建模 · 音乐 · 交易 · 管理科学 · 家教 · 小说 · 篆刻 · …

一重身份 = 一套目标 + 一批资料 + 一类产出 + 一种节奏。当系统只有「任务」
这一个抽屉时，9 重身份的东西全被塞进同一个抽屉 —— **你不是没在推进，
你是没法一眼看出自己在推进哪一条线**。这就是「乱」的来源。

### 2.2 加重原因：81% 的成果在数据库外

扫描 `D:\YanYuas` 的结果：

| | 数量 |
|---|---|
| 总文件 | 10,558（3.2 GB） |
| 其中噪声（venv / node_modules / .git / __pycache__ / .pyc） | **约 81%** |
| 真实内容 | **1,961** |
| 构成 | `.md` 370 · `.py` 423 · `.html` 271 · `.docx` 150 · `.pdf` 78 · `.vue` 33 |

**你真正的人生历程、兴趣与成果，81% 不在系统里。**系统记的是「你打算做什么」，
而你过去几年「已经做了什么」全躺在 D 盘的目录树里。这两半没有接上，
所以系统看起来总像「一个待办清单」，而不像「你的人生操作系统」。

### 2.3 一句话总结

> **系统有很强的时间轴（任务/复盘/成长），但缺一根身份轴，也缺一根档案轴。**
> 三期就是补这两根轴，再把高敏数据（凭据）单独封进保险箱。

## 三、目标架构：三层

```
┌─────────────────────────────────────────────────────────┐
│  L1 身份层（阶段 B）                                     │
│  9 重身份 = 横切维度，任务/项目/文档/资源都挂 identity_id │
│  解决：我在推进哪一条线？                                 │
├─────────────────────────────────────────────────────────┤
│  L2 工作区 / 档案库（阶段 C）                             │
│  索引 D 盘真实文件 + 一键开终端 + 路径白名单               │
│  解决：我已经做了什么？在哪？怎么立刻开始干活？             │
├─────────────────────────────────────────────────────────┤
│  L3 保险箱（阶段 D）                                      │
│  主密码解锁 · 凭据/密钥/账号 · 只存密文 · 空闲自动锁       │
│  解决：高敏数据敢不敢放进来？                             │
└─────────────────────────────────────────────────────────┘
        ↑ 阶段 E（邮箱站）依赖 L3 存邮箱凭据
```

**架构铁律（继承二期，不得违反）**：

1. 四层分层不可跨层：`api/` → `services/` → `repositories/` → `models/`
2. 新迁移必须写幂等守卫（`app/migration_helpers.py`）—— `0001_initial.py`
   用 `create_all()` 建的是「当前全部模型」，无守卫会让全新库起不来
3. 设计令牌唯一来源 `frontend/src/styles/variables.scss`，组件内不写 `#`
4. **数据主权不迁移**：档案库只索引路径，不把 D 盘内容搬进数据库

## 四、阶段 B｜身份层（推荐第一个做）

### 4.1 为什么先做它

它是所有后续阶段的**分类轴**。档案库扫出来的 1961 个文件要按身份归类，
保险箱的凭据要挂在身份下，报告导出要按身份筛选 —— 身份层不先立起来，
后面每一步都得返工。

### 4.2 设计取舍：横切标签，不是第五个模块

**关键决策（推荐）**：身份不做成新的顶层导航项，而是做成**横切维度**：

- 顶栏加一个全局「身份筛选器」（下拉 + 配色点），选中后所有列表（任务/项目/
  文档/资源）自动按 `identity_id` 过滤；
- Dashboard 从「一堆统计卡片」改为「按身份分组的进度阵列」；
- 新建任务/项目时多一个身份选择（可空，表示「未归类」）。

**为什么不另起模块**：另起一个「身份页」等于把同一个任务在两个地方记两遍，
这正是 S6-4 结构化经历卡住的原因（已经有 Diary / Review / AvatarMemory /
ProjectMemory 四处记「发生过什么」）。**横切标签可以后加、可以为空、
不会制造第二份真相**。

### 4.3 数据模型（迁移 0015）

```python
# models/identity.py
class Identity(UUIDMixin, TimestampMixin, SoftDeleteMixin, SyncMixin, Base):
    __tablename__ = "identities"
    user_id      # FK users
    name         # 显示名：AI 研究
    slug         # 唯一键：ai-research
    color_token  # 只允许令牌名（如 --primary），不存 # 色值
    icon         # AppIcon 名
    description
    sort_order
    is_active    # 归档的身份不参与筛选器，但历史数据保留
```

**给已有表加外键**：`tasks` / `projects` / `documents` / `resources` 增加
可空 `identity_id`。用 `add_column_if_missing` 守卫，且**不加外键约束**
（SQLite 加约束要重建表，风险大），只做应用层关联。

### 4.4 工作量与验收

| 项 | 内容 |
|---|---|
| 后端 | `models/identity.py` + 0015 迁移 + `identity_service.py` + `api/identity.py`（CRUD 5 端点）+ 4 张表加列 |
| 前端 | 全局身份筛选器组件 + Dashboard 分组 + 新建表单身份选择 + `views/Identity`（管理页，hidden） |
| 估算 | 3–4 个工作日 |
| 验收 | ① 建 9 个身份后，选中「音乐」时任务列表只剩音乐相关；② Dashboard 按身份分组显示；③ 新建库全新迁移可通过；④ 冒烟新增 ≥ 6 条断言 |

### 4.5 风险

- **历史数据无身份** —— 全部为 `null`，靠「未归类」兜底，不强制回填。
  可后续用 `skill_cats` 关键词做一次批量建议归类（人工确认）。
- **身份泛滥** —— 建议上限 12 个，超了说明该合并而不是新建。

## 五、阶段 C｜工作区 / 档案库

> 这是你最初的想法：「让启明星连到资源管理器，进文件夹就能 CMD 开终端做 AI 编程」。

### 5.0 可选功能 + 引导部署（2026-09-16 用户决策，优先级高于本节其余内容）

**工作区必须做成可选择功能**：别人的电脑上文件夹结构与作者不同，
因此本模块——

- **默认关闭、零预设**：`settings["workspace.enabled"]="false"`，
  不存在"内置 D:\YanYuas"这种东西。作者的本机路径只是作者自己的
  实例，不是产品的默认值；
- **引导式部署**，目录结构两条路建立：
  1. **登记现有文件夹** —— 用户把自己已有的目录登记为工作区根；
  2. **按身份生成目录骨架** —— 在根下为每个活跃身份创建同名文件夹。
     结构原则与作者一致（一重身份一个文件夹），但名字来自
     **用户自己的身份**，而非作者的目录名 —— 这才是"引导他们将
     文件夹弄成我这样"的正确实现：迁移的是组织原则，不是路径；
- 前端在引导完成前不展示工作区入口；引导向导（启用 → 登记/生成
  → 扫描 → 完成）是 C 阶段前端的第一个界面。

### 5.1 做什么

1. **登记根**：把 `D:\YanYuas`（真根）和 `C:\Users\21722\Desktop\YanYuas`（轻量/指针）
   登记为工作区根；
2. **扫描索引**：增量扫描，过滤 81% 噪声，落 `workspace_files` 表；
3. **档案库页面**：按身份 / 类型 / 时间筛选，文件名搜索，看最近改动；
4. **一键开终端**：在档案库里对任意目录点「在这里打开终端」，后端拉起终端。

### 5.2 数据模型（迁移 0016）

```python
class WorkspaceRoot(...):
    user_id, path, label, identity_id(可空),
    enabled, scan_status, last_scanned_at, file_count, total_size

class WorkspaceFile(...):
    root_id, rel_path, name, ext, size, mtime,
    identity_id(可空，先按根/路径规则继承，再交给用户改),
    is_noise, indexed_at
```

### 5.3 三个必须写对的地方

**① 噪声过滤（决定成败）**

扫描实测噪声占 81%，不过滤的话索引表会被 8000 多条 `.pyc` 淹没。
黑名单（目录）：`node_modules` `venv` `.venv` `__pycache__` `.git` `dist`
`build` `.idea` `.vscode` `site-packages`；
黑名单（扩展名）：`.pyc` `.pyo` `.log` `.tmp` `.DS_Store` `*.egg-info`。
规则**存 settings 表**（A3 刚通的能力），用户可改，不写死在代码里。

**② 路径白名单（安全红线）**

终端集成的本质是「让 Web 前端能在本机启动进程」，这是本项目**风险最高的功能**。
硬约束：

- 只允许操作**已登记 root 之内**的路径；
- 用 `Path.resolve()` + `is_relative_to(root)` 双重校验，拒绝 `..` 穿越；
- 拒绝符号链接指向 root 之外的目标（桌面 `.lnk` 指针必须解析后校验真实目标）；
- 命令白名单：只允许「打开终端」这一个动作，不提供任意命令执行接口。

**③ 扫描性能**

1961 个真实文件不算多，但每次都要走完 10558 个路径。用 `os.scandir()`
按目录递归 + 黑名单剪枝（命中即不进入子树），首次全量应在 10 秒内；
增量按 `mtime + size` 跳过未变文件。

### 5.4 终端拉起方式（本机 Windows）

优先级：`wt.exe -d "<path>"`（Windows Terminal）→ 回退
`cmd /c start cmd /K cd /d "<path>"`。
用 `subprocess.Popen` + `creationflags=DETACHED_PROCESS`，**不等待、不捕获输出**
（否则后端进程会挂住）。终端类型存 settings，可切 PowerShell。

### 5.5 工作量与验收

| 项 | 内容 |
|---|---|
| 后端 | `models/workspace.py` + 0016 迁移 + `workspace_service.py`（扫描/剪枝/白名单）+ `api/workspace.py`（根 CRUD / 扫描触发 / 文件列表 / 打开终端 4 类端点） |
| 前端 | `views/Workspace/`：根列表 + 文件浏览器 + 筛选 + 「在此打开终端」按钮 |
| 估算 | 4–5 个工作日 |
| 验收 | ① 登记 `D:\YanYuas` 后扫描，索引条数 ≈ 2000（不是 10558）；② 点「打开终端」能在正确目录拉起；③ 传入 `../../Windows` 之类路径被拒绝；④ 冒烟新增 ≥ 8 条断言（含穿越防护） |

## 六、阶段 D｜保险箱（凭据库）

> 密钥保存站 + 账号汇总站合并为「保险箱」。这两个本质是一件事：**高敏字符串的
> 加密存取**，分开做会出现两套主密码、两套解锁逻辑，属于自找麻烦。

### 6.1 主密码模型

```
主密码 --PBKDF2(随机 salt, 高迭代)--> 数据密钥
                                        │
                    加密单条凭据的 secret / notes
                                        │
                    密文进 vault_entries（明文永不落盘）
```

**必须先修的一处**：`core/encryption.py:36` 现在的 salt 是硬编码的
`b"venustech_system_salt_2026"`。固定 salt + 已知迭代次数 = 主密码可被彩虹表
预计算攻击。保险箱启用前要改成**随机 salt 存库**（迁移 0017 顺带处理）。

### 6.2 解锁与锁定

| 规则 | 设计 |
|---|---|
| 解锁 | 前端提交主密码 → 后端派生密钥 → 只返回短期 token，**密钥只驻留内存** |
| 落盘 | 主密码、派生密钥、token **一律不落盘**（不进 localStorage、不进 DB、不进日志） |
| 自动锁 | 空闲 10 分钟锁定（时长存 settings）；锁定时清空前端所有已解密内容 |
| 剪贴板 | 复制后 30 秒自动清空（前端定时 `navigator.clipboard.writeText('')`） |
| 忘记密码 | **无后门**。见 §9 D8 |

### 6.3 数据模型（迁移 0017）

```python
class VaultEntry(...):
    user_id, identity_id(可空),
    kind          # credential | api_key | note
    title, site, url, username,
    secret_enc    # 密文，列表接口不返回
    notes_enc     # 密文
    expires_at, last_used_at
```

**API 设计要点**：`GET /vault` 返回列表但**不含 secret**；
必须单独 `POST /vault/{id}/reveal` 且要求已解锁 —— 这样即使列表接口被
误调用或日志被抓取，也泄漏不出明文。

### 6.4 工作量与验收

| 项 | 内容 |
|---|---|
| 前置 | 修固定 salt（`core/encryption.py` + 0017 迁移） |
| 后端 | `models/vault.py` + `vault_service.py`（解锁/锁定/加解密/导出）+ `api/vault.py` |
| 前端 | `views/Vault/`：解锁页 + 列表 + 详情（reveal 需二次确认）+ 复制到剪贴板 |
| 估算 | 3–4 个工作日（含 salt 修复） |
| 验收 | ① 未解锁时 `reveal` 被拒；② 数据库文件里 `grep` 不到任何明文；③ 空闲超时自动锁；④ 加密导出文件能在全新库导入还原；⑤ 冒烟新增 ≥ 8 条断言 |

## 七、阶段 E｜邮箱站（**先评估，别急着做**）

### 7.1 依赖

邮箱站需要存邮箱账号密码 → **依赖阶段 D**。所以顺序上必然在 D 之后。

### 7.2 建议：先做 E0，验证价值再投入

个人自用场景下，邮箱站的真实需求值得怀疑：你每天是**在启明星里看邮件**，
还是**打开浏览器看邮件**？如果是后者，做它的唯一收益是「未读数聚合」。

**E0（0.5 天，验证用）**：不做收发，只在 Dashboard 加一个「未读邮件」卡片，
通过 IMAP 只读拉取各邮箱未读数，每 10 分钟刷新。跑两周，看你是否真的会看它。

- 会看 → 做 E1（邮件列表 + 搜索 + 标记已读），仍然只读；
- 不看 → **砍掉**，把时间投到 B/C 的深度上。

### 7.3 明确不做

- **OAuth 授权**（Gmail / Outlook）—— 客户端 ID 申请、token 刷新、合规，
  投入产出比极差。只支持 IMAP + 应用专用密码 / 授权码。
- **发邮件**（SMTP）—— 写邮件的需求在客户端里解决更好，且风险高。

## 八、阶段 F｜赛程 / 竞赛资料分析（**降级为可选**）

原始想法是「赛程资料分析」。重新评估后建议**降级**：

- 赛程数据没有稳定来源，抓取与维护是长期负担；
- 「分析」需要明确的分析目标（分析什么？给谁看？），目前没有；
- 真正的痛点是**资料散落在 D 盘**——这已经被阶段 C 解决了。

**替代方案**：竞赛作为**一个身份**（`identity.slug = 'contest'`）+ 档案库里
