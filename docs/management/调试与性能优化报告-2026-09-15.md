## 二、B-1（P0）· 全新数据库迁移崩溃

### 现象

在干净的数据库上启动后端，迁移链在 `0009` 处中断：

```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) table workflows already exists
[SQL: CREATE TABLE workflows (...)]
```

**影响**：任何全新部署（新机器、新开发者、CI、清空数据重来）都无法启动。老开发者察觉不到——因为仓库里提交了一个已经建好表的历史 `app.db` 掩盖了问题。

### 根因

`backend/migrations/versions/0001_initial.py:21`：

```python
def upgrade() -> None:
    bind = op.get_bind()
    Base.metadata.create_all(bind)      # ← 建的是"当前代码里注册的全部模型"，不是 0001 当时的 schema
```

实测确认：`app/database.py` 导入 `app.models.base`，会连锁触发 `app/models/__init__.py`，把**全部 39 张表**注册进 `Base.metadata`（已实测 `len(Base.metadata.tables) == 39`，含 `workflows`）。

于是全新库上：

| 迁移 | 实际情况 |
|------|----------|
| 0001 | `create_all` 一次把 **39 张表全建了** |
| 0002/0003/0005/0008 | 写了 `_table_exists()` 幂等守卫 → 安全跳过 ✅ |
| **0009/0010/0011** | **无守卫，直接 `op.create_table` → 撞已存在的表，迁移中断** ❌ |

即：**只有 0008 及之前做了幂等，0009 之后的三次迁移漏了**。

### 修复

给 0009 / 0010 / 0011 补上与 0008 完全一致的幂等守卫（`_table_exists` / `_index_exists`），并让 `downgrade()` 同样按存在性判断。**沿用项目既有写法**，不引入新模式。

### 验证

```
修复前：迁移在 0009 中断 → 冒烟测试无法运行
修复后：迁移 0001→0011 全程通过 → 冒烟结果: 28 通过, 0 失败
```

另：日志里 `0008_new_modules: 15 tables created` 是**硬编码的陈旧打印**（0008 实际建了 0 张表），已确认无功能影响，但建议后续修正以免误导排障。

## 三、B-2（P0）· 架构守护测试形同虚设

### 现象

`tests/test_architecture.py` 明确断言「api 层禁止运行时 import models」，但实测**有 7 个文件违反**：

```
asset.py · avatar.py · learning.py · life.py · pet.py · resource.py · workflow.py
```

而《一期模块考校报告》第 2.2 节记为「后端架构测试 ✅ 分层依赖检查通过」。

### 根因

**该测试从未被执行过**——本机 venv 未安装 pytest（正是考校报告自己记录的 E-01 环境问题）。守护测试写了却跑不了，违规便悄悄累积了 7 处。考校报告里那句「通过」是照抄文档，不是实测。

### 违规性质（重要）

逐文件核查后确认：这 7 处**只是为 `user: User = Depends(...)` 的类型标注**导入模型，**没有任何直接查库**（已用脚本验证「运行期引用 = 无」）。所以**没有实际的架构腐化**，只是触碰了测试的字面规则。

关键点：该测试**本身就内置了 `TYPE_CHECKING` 豁免**：

```python
cleaned = re.sub(r"if TYPE_CHECKING:.*?(?=\n\S|\Z)", "", content, flags=re.DOTALL)
assert "from app.models" not in cleaned
```

说明测试作者预料到了这种情况并留了正式出口。

### 修复

1. 把 7 个文件的模型导入移入 `if TYPE_CHECKING:` 块（7 个文件均已有 `from __future__ import annotations`，注解保持惰性）。
2. **先验证风险再做**：FastAPI 会在运行时解析端点注解，担心 `TYPE_CHECKING` 引发 `NameError` —— 实测 `/api/v1/learning/plans` 返回 **200**，确认安全（参数用 `Depends` 注入，不需要运行期名字）。
3. 给 `test_architecture.py` 加**免 pytest 运行入口**，让守护真正可执行：

```bash
cd backend && python tests/test_architecture.py
# 架构守护结果: 5 通过, 0 失败
```

> 修完 7 个文件后：2/5 通过 → **5/5 通过**。

## 四、B-3（P1）· 首页「今日执行」统计口径错误

### 现象

首页「今日执行」卡片显示的 `total` 与各分组数量对不上，且与同一屏的「今日统计」自相矛盾：

- `today_stats.must_do` = 只数**今日到期**的任务（可能是 2）
- `today_execution.total` = **全部任务数**（可能是 57）

用户看到「共 57 项」但分组之和只有几项。

### 根因

`services/dashboard_service.py` 原实现：

```python
count=sum(1 for t in all_tasks if t.status == status),   # 全体同状态任务数，不分日期
...
return TodayExecution(groups=groups, total=len(all_tasks))   # 全部任务
```

两处都用了「全体任务」，与「今日执行」语义不符。

**同一函数内还有第二个缺陷**：`all_tasks` 来自 `task_repo.list_user_tasks()`，该查询**没有 ORDER BY**，所以「每分组取前 5 条」取到的是数据库返回的任意顺序——**逾期任务可能被挤掉**。

### 修复

1. 新增 `_is_actionable_today()` 明确「今天要动手」的口径：进行中/等待处理天然计入；待办仅当**今日到期或已逾期**才计入；**无截止日期的待办不计入**（属"以后再说"）。
2. `total` 改为**各分组 count 之和** → 自洽。
3. 增加排序：**已逾期 → 今日到期 → 无期限 → 未来到期**，同级按优先级。

### 验证（已固化为回归断言）

在 `scripts/smoke_backend.py` 新增 4 条断言，防止回归：

```
✅ today_execution: total == 各分组之和
✅ today_execution: 排除无截止日的待办
✅ today_execution: 纳入今日到期待办
✅ today_execution: 纳入后仍自洽
```

> 这 4 条断言在**修复前会失败**（旧代码 total=2 而分组之和=1），具备真正的判别力。

## 五、性能优化

### P-1 · `StringListType` 缺少编译缓存键

**现象**：冒烟测试输出 `SAWarning: TypeDecorator StringListType() will not produce a cache key because the cache_ok attribute is not set to True. This can have significant performance implications`，指向 `document_repo.py:74`。

**根因**（已定位到 SQLAlchemy 源码级）：

```python
# sqlalchemy/sql/type_api.py:1290
cache_ok = self.__class__.__dict__.get("cache_ok", None)
if cache_ok is None:
    util.warn("... will not produce a cache key ...")
```

判定用的是 **`self.__class__.__dict__`——只看类自身声明，不认继承**。`StringListType` 继承自 `JSONType`（后者已有 `cache_ok = True`），但未在自身 `__dict__` 声明，于是被判为「无缓存键」。

**修复**：在 `StringListType` 类的 `__dict__` 中显式声明 `cache_ok = True`，并加注释说明这个继承陷阱。

**验证**：
```
修复前：_static_cache_key → None（无缓存键，告警）
修复后：_static_cache_key → (<class 'app.models.types.StringListType'>,)  ✅ 无告警
```

**诚实说明**：我尝试量化它的运行时收益，做了 A/B 压测（300 次 `SELECT documents.tags`）：

```
修复后: 173.1 微秒    修复前: 169.8 微秒    差异 -2%（属噪声）
```

**没有测出可测量的性能提升**。原因有二：① 该查询过于简单，编译成本本就极低；② 我事后用 monkeypatch 模拟修复前状态**并不可靠**——SQLAlchemy 在 mapper 配置阶段就固化了类型键，事后改 `cache_ok` 无法真正复现旧行为（实测两种情况编译缓存条目数都是 1）。

所以这项应定性为**正确性/卫生性修复**：消除了一条真实告警，并恢复了含 `documents.tags` 语句走编译缓存路径的能力。收益随语句复杂度上升，在当前简单查询上不显著。

### P-2 · 首页单次请求 27 条 SQL

**实测基线**：

```
dashboard HTTP: 13.0 ms / 27 条 SQL（全部 SELECT）
```

**问题**：有 10 处「只为读一个总数」却付出了完整查询代价：

```python
card_count = self.learning_svc.list_cards(self.user.id, page=1, page_size=1)["total"]
```

`BaseRepository.paginate()` 内部是 `list()`（SELECT ... LIMIT 1）+ `count()`（COUNT）**两条 SQL**，还会 hydrated 一个 ORM 对象——纯粹为读一个数字。而 `BaseRepository.count()` **本来就有**，只是没人用（`FlashcardRepository.count_by_user` / `count_due_today` 甚至已经写好却闲置）。

另有一处 `len(resource_svc.list_domains(...))`：为了取长度而**加载全部领域对象**。

**修复**：给 `DashboardService` 注入对应 Repository，把 10 处换成直接 `COUNT`：

| 调用点 | 修复前 | 修复后 |
|--------|--------|--------|
| 收集箱 / 模板 / 领域 | 2 + 2 + 全量加载 | 3× COUNT |
| 卡片总数 / 今日待复习 | 2 + 全量加载 | 2× COUNT（复用已有方法） |
| 习惯 | 2 | 1× COUNT |
| SOP / Prompt / Skill / 项目记忆 | 4×2 | 4× COUNT |

**实测收益（同口径对比）**：

```
优化后 · 首页服务层  :  5.06 ms / 18 条 SQL
被消除的旧路径开销    :  2.97 ms / 18 条 SQL（占服务层 59%）
服务层净耗时         :  8.03 ms → 5.06 ms   ↓ 37%
SQL 语句数           :  27 → 19              ↓ 30%
```

分层合规：`services → repositories` 是允许的方向，架构守护 5/5 通过。

### 为什么没有更快？——测出来的真相反驳了我的假设

我原以为瓶颈在 SQL 条数，于是做了耗时构成剖析：

```
单次总耗时        : 14.60 ms
其中 SQL 执行     :  0.99 ms  ( 7%)
其余(Python/序列化): 13.61 ms  (93%)
```

进一步用 cProfile 剥离（`TestClient` 的 ASGI 测试脚手架本身约 9.8 ms，不是真实成本）后：

```
仅服务层 get() = 4.76 ms
热点：SQLAlchemy ORM 层固定开销 —— 单条语句约 0.2 ms，
      而 SQLite 实际执行仅约 0.02 ms（ORM 开销是实际查询的 ~10 倍）
```

**结论：瓶颈是 ORM 层的每语句固定开销，不是数据库本身。** 所以要提速只能减少语句数——这正是 P-2 做的事。这也解释了为什么首次 HTTP 层测量（13.0 → 12.84 ms）看不出改善：测试脚手架的 10ms 波动淹没了 1.6ms 的真实收益。

### 索引：实测无问题（未做无谓改动）

我对 11 个关键查询跑了 `EXPLAIN QUERY PLAN`：

```
tasks: user_id / user_id+status / user_id+due_date        ✅ 走索引
documents: user_id ORDER BY updated_at                    ✅ 走索引
flashcards: user_id+next_review                           ✅ 走索引
habit_checkins / project_memories / sops / prompts /
skills / habits: user_id                                  ✅ 走索引
```

34 张表建有索引；无索引的 5 张是 `alembic_version`、`avatar_configs`、`pet_configs`、`settings`、`users`——均为单行配置表，**不需要索引**。

**索引覆盖良好，无需优化。**

## 九、第二轮新发现：4 个「静默失效」的功能

这些都具备同一特征——**功能看似存在，实则永不生效，且没有任何日志**。它们能长期存活，正是因为
`except Exception: pass` 与 `hasattr` 兜底的组合把失败伪装成了"正常但没数据"。

### S-1（P1）· 桌宠「状态感知」整体失效

`services/pet_service.py` 的 `get_current_state()` 是桌宠"有感知的陪伴者"这一卖点的实现。实测两处死代码：

| 位置 | 问题 | 后果 |
|------|------|------|
| L136 | `list(status="todo")` —— 但合法状态只有 `pending/in_progress/waiting/completed`（`Task.status` 默认 `pending`），**`todo` 永远匹配不到** | `todo_count` 恒为 0 → 「专注中」动作与"还有 N 个任务待完成"气泡**永不触发** |
| L153 | `getattr(moods[0], 'mood')` —— 但 `MoodLog` 表只有 `score/tags/content/logged_date`，**没有 `mood` 列**，`hasattr` 恒为 False | `recent_mood` 恒为 None → 桌宠心情**永远显示「平静」** |

**修复**：任务感知改用 `count_due_today_open()`（语义正确且与首页 `must_do` 同口径）；
心情感知改为按 `score(1-5)` 经 `MOOD_SCORE_MAP` 映射到心情键。

**验证**：
```
3个今日待办 + 1未来 + 1已完成 → todo_count = 3（期望 3）✓
心情分 5 → happy/开心 | 3 → neutral/平静 | 1 → sad/难过 ✓
```

> 附带发现（未改）：`MOOD_BUBBLES` 三元组是 `(中文标签, 动作键, 气泡)`，而代码写的是
> `mood_label, mood, mood_bubble = ...` —— 于是响应里的 `mood` 字段装的其实是**动作键**
> （如 sad → `"caring"`）。命名与内容不符，但已是被前端消费的既有契约，擅自改动会破坏兼容，
> 故仅记录。

### S-2（P1）· 健康检查双重失效

`api/health.py` 的两个函数**恒返回错误值**：

| 函数 | 问题 | 实测 |
|------|------|------|
| `_check_db_connection()` | `conn.execute("SELECT 1")` 传裸字符串，SQLAlchemy 2.0 抛 `ObjectNotExecutableError` 被吞 → **数据库明明可连却永远报「未连接」** | 修前 `False` → 修后 `True` ✓ |
| `_get_db_size()` | 读 `settings.database_url`，但 Settings **没有该属性**（实际叫 `db_url`），`getattr` 恒取 `""` → 判断永不成立 → **数据库大小恒为 0 MB** | 修前 `0.0` → 修后 `0.62 MB` ✓ |

**影响面**：`/health/detailed` 与 `/system/info` 都被前端设置页与 Electron 主进程轮询用于判断后端就绪。

**修复**：`text("SELECT 1")` 包裹 + 直接使用 `settings.db_path`（已是 Path，比解析 URL 可靠）。

### S-3（P1）· AI Key 校验把一切错误报成「Key 无效」

`verify_api()` 把所有异常吞成 `valid=False`。用户看到"Key 无效"，**但真实原因可能是网络不通
或服务 5xx** —— 会让人反复重填一个本来就正确的 Key，而日志里零痕迹。

**修复**：区分 HTTP 401/403（Key 无效）与其他失败（服务不可用/请求异常），记录日志并回传原因。
`ApiVerifyResult` 新增 `reason: str = ""`（可加性，向后兼容）。

### S-4（P2）· AI 客户端静默退回 Mock

`get_llm_client()`：用户**已配置 Key 但解密失败**（加密密钥轮换、密文损坏）时静默返回 `MockLLMClient`，
用户看到的是"（演示模式）模拟回复"，与从未配置 Key 无法区分。**修复**：补 warning/exception 日志。

### 关于 171 处硬编码颜色的诚实说明

项目硬约束写明「组件文件内 `grep '#'` 零命中」，实测**大范围未落实**。但我**没有批量替换**，原因是：

1. 59 种色值里**只有 `#fff`（17 处）在令牌体系中存在**，其余 58 种（如 `#7c5cff`、`#ff4d4f`、`#52c41a`、`#faad14`）**根本不在设计令牌里** —— 那是 Element Plus / Ant Design 默认色与组件自创色的混合。
2. 机械替换会**改变产品视觉外观**，需要设计决策（是收编进令牌、还是改成现有令牌的近似值？）。
3. 我无法在本环境目视验证 UI 变化，盲改 171 处等于把视觉风险留给用户。

因此正确做法是：**给出精确数字 + 可复跑工具 + 棘轮阈值**，让这件事变成可管理的债务，而不是一次性高风险的机械重构。
