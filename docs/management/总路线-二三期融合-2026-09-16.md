```
                        2-3d                   观察期与 S6-3b 并行）
```

**一句话逻辑**：先用身份轴把二期的两个卡壳项（S6-4、S6-5）顺化解掉，
再连接文件系统（C），然后封保险箱（D）、通同步（S6-3b），
最后才是生态验证（S6-6 / E1）。

### 为什么是这个顺序（防返工的三条主线）

1. **身份轴先行** → S6-4 从「建经历库」降维成「建视图」，S6-5 的报告
   天然带身份分组。反过来做，两个都要返工（见 R1 / R3）；
2. **sync 引擎殿后** → 表集合稳定后再写引擎，且把 vault / workspace 的
   特殊性一次设计进去（见 R2）。本地优先架构允许它晚做，不欠账；
3. **报告三轴齐了再导出** → B（身份）× W2（成长）× C（档案）都就位后，
   「人生报告」一次做对，不用二次改模板（见 R3）。

## 二、返工风险清单（核心章节，动工前必读）

### R1 · S6-4 结构化经历 × 身份层 —— 最大的一个返工点

**二期原状**：S6-4 卡死在「概念归并」—— Diary / Review / AvatarMemory /
ProjectMemory 已经四处记「发生过什么」，再建一张经历表 = 同一件事记五遍，
所以二期正确地把它挂起了。

**融合后解法**：B 落地后，这四张表都有了 `identity_id`。
「一个人的经历」就可以定义成：

> **经历 = 按身份聚合的四源时间线视图（数据库 VIEW 或服务层聚合查询），不建新表。**

- 归并问题被身份轴解开：四源不合并存储，只在**读取时**按 identity 聚合；
- S6-4 的工作量从「新表 + 迁移 + 双写兼容」降到「一个聚合查询 + 一个页面」；
- **硬约束**：S6-4 严禁新建经历表。将来若聚合查询性能不够，再加物化，
  也不改变「不制造第二份真相」的原则。

⇒ **顺序约束**：S6-4 必须在 B 之后。在 B 之前动 S6-4 = 白做。

### R2 · S6-3b diff-sync × 新增表 —— 引擎设计必须预留「表分级」

三期会新增至少 4 张表（identities / workspace_roots / workspace_files /
vault_entries），42 → 46+。它们都已按铁律继承 SyncMixin，字段层面**零返工**；
真正的返工风险在**引擎设计**里：

| 表 | 同步策略 | 若引擎不考虑会怎样 |
|---|---|---|
| identities 等常规业务表 | 正常 diff-sync | — |
| `workspace_files` | **不同步**（派生数据，重扫即得，量又大） | 同步流量被几千行索引文件淹没 |
| `vault_entries` | 同步**密文**列，不同步明文派生数据 | 明文泄漏进同步通道 |
| settings | 同步（但只同步非设备相关键） | 终端路径等本机配置污染另一台机器 |

⇒ **设计约束**：S6-3b 的 `core/sync.py` 必须内置 **SYNC_POLICY 表分级**
（`full` / `derived-skip` / `encrypted-only`），做引擎的那一天就要有这个配置项，
不能事后补。⇒ **顺序约束**：放 D 之后，表集合稳定、vault 语义明确后一次做对。

### R3 · S6-5 报告导出 × 身份轴 + 档案轴 —— 模板别做两遍

报告的分组维度决定模板结构：

- 若在 B 之前做：只能按模块分组（任务/复盘/…），B 落地后要重写模板；
- 若在 B 之后、C 之前做：有身份分组，但「人生报告」缺了档案库的成果统计
  （1961 个文件、按身份的产出分布）—— 这恰是用户最想被报告回答的问题
  「我这段时间产出了什么」。

⇒ **顺序约束**：S6-5 放 C 之后，定位升级为**「人生报告」**：
身份 × 成长（EXP/等级）× 档案（文件产出）三轴合一，单文件 HTML，一次做对。

### R4 · 硬编码颜色 171 处 —— 禁止大爆炸清理

大爆炸改 16 个文件 = 一次巨大 diff，行尾符事故（W0 教训）和回归风险都高，
且与任何功能无关的改动最难 review。

⇒ **约定**：**触达即清** —— B/C/D 每个阶段反正要改前端文件，改到哪个文件
就把该文件的硬编码色顺手清掉；每阶段收尾跑
`python scripts/audit_hardcoded_colors.py`，**数字不得增加、应逐阶段递减**。
B 阶段新增的 GrowthView / 身份筛选器等一律零硬编码（A1 已守约）。

### R5 · Electron 打包 —— 降级为可选增强

二期阶段五计划 Electron。C 阶段的终端集成用「本地后端 subprocess + 浏览器」
方案已可用（三期规划 §5.4），Electron 不是前置条件。且 Electron 打包反而
会让 C 的路径白名单、终端拉起多一套要测的环境。

⇒ **决定**：Electron 从「阶段五必做」降级为「C 之后的可选增强」，
触发条件：你真的需要「不带浏览器窗口的原生体验」时再启动。

### R6 · 前端零测试 —— 只补「改动面最大」的守卫

不追求覆盖率。只在身份筛选器（B，全局横切组件，改动面最大）落地时，
顺手补 2–3 条关键路径组件测试（筛选切换 → 列表过滤 → Dashboard 分组）。
其余维持「冒烟 + 类型检查 + 架构守护」三道防线不变。

### R7 · 技能分类扩容 / 升级庆祝反馈（S6-2 收尾）

纯数据 + 纯前端反馈，与任何阶段无耦合。归入 B 阶段顺手做
（B 要动 Dashboard 和成长页周边，顺路），不单独立项。

## 三、统一执行顺序（逐阶段卡片）

### 波次一「立轴」：B 身份层 → S6-4 经历视图（约 5–6 天）

**B 身份层**（3–4d）—— 按三期规划 §4 执行，补充两点：
- 迁移编号接 0015；
- 新增 `identity_id` 时**同步给 Diary / Review / AvatarMemory / ProjectMemory**
  也挂上（原计划只挂 tasks/projects/documents/resources 4 张）——
  这是 R1 解法的前提，一天内多做的量，省掉 S6-4 的整个概念归并。

**S6-4 经历视图**（1–2d）—— 重定义后开工：
- 服务层聚合查询：四源按 identity + 时间排序归并；
- 前端「经历时间线」页（hidden 路由，从身份筛选器进入）；
- 验收：选一个身份，能看到该身份下横跨四源的全部「发生过什么」；
  **全仓库 grep 不到新的经历表**。

### 波次二「连接」：C 工作区 / 档案库（约 4–5 天）

按三期规划 §5 执行，无顺序修正。补充两点：
- 噪声规则、终端类型**必须**走 settings 表（A3 的白名单机制现成），
  为 R2 的「settings 分级同步」提前铺路；
- 顺手清掉所触前端文件的硬编码色（R4）。

**2026-09-16 用户决策追加（见三期规划 §5.0）**：工作区是**可选功能
+ 引导式部署** —— 默认关闭、零预设；目录结构由引导向导建立
（登记现有文件夹，或按用户自己的身份一键生成骨架）。前端第一步
就是引导向导，不是文件浏览器。

### 里程碑：S6-5 人生报告导出（2–3 天）

- 单文件 HTML，三轴合一：身份分组 → 每身份下的任务/复盘/成长/档案统计；
- 复用 backup 导出的下载链路；
- 这是 B+C 之后第一个「能发朋友圈」级别的产出，也天然是阶段验收物。

### 波次三「安全 + 同步」：D 保险箱 → E0 → S6-3b（约 7–8 天）

**D 保险箱**（3–4d）—— 按三期规划 §6 执行。第一步就是修
`core/encryption.py:36` 的硬编码 salt（迁移 0017）。

**E0 邮箱验证**（0.5d）—— 紧跟 D（要存 IMAP 授权码）。启动后进入
**两周观察期**：期间正常推进 S6-3b，观察期结束按数据决定 E1 做不做。

**S6-3b diff-sync**（3–4d）—— 按二期日志 §六.A 执行，叠加 R2 的
**SYNC_POLICY 表分级**为第一天设计项。验收增加一条：
`workspace_files` 与 `vault_entries` 在同步清单中的策略符合表分级定义。

### 波次四「验证 + 生态」：S6-6 AI HOT 插件（1–2 天，可随时穿插）

无耦合，谁先谁后都行。放在最后的唯一理由：它是「锦上添花」，
前面任何阶段延期都不应该被它挤占。
