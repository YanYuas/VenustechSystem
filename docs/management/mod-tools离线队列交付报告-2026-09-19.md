## 一、交付内容

| 文件 | 职责 |
|---|---|
| `src/utils/offlineQueueCore.ts` | **纯逻辑核心**：FIFO 重放、失败计数、上限停止、重试全部、清空失败；存储与发送通过接口注入，可脱离浏览器单测 |
| `src/utils/offlineQueueIdb.ts` | IndexedDB 持久化（库 `venustech_offline_queue` / 表 `queue` / 自增主键 id） |
| `src/stores/offlineQueue.ts` | Pinia store：状态 + online/offline 监听 + 事件广播 |
| `src/api/http.ts` | 写操作拦截：离线或网络失败时入队，抛 `OfflineQueuedError` |
| `src/components/layout/OfflineQueueIndicator.vue` | 右上角角标 + 底部抽屉面板（重试全部 / 清空失败） |
| `src/components/layout/TopNav.vue` | 挂载角标 |
| `src/app/main.ts` | 注册入队钩子 + 启动时初始化队列（读存量 + 挂监听） |
| `scripts/test-offline-queue.ts` | **15 条核心行为测试**（esbuild 转译 + node 运行） |

**为什么核心要拆成纯模块**：队列逻辑（FIFO、重试上限、并发保护）**只在离线时才会跑**，
真机上极难复现，一旦写错就是"离线记的待办全丢了"。拆出纯核心后可以在 Node 里
用内存存储 + mock 发送器穷举各种失败路径。

## 三、状态语义（写进代码注释，避免以后误解）

```
pending  —— 队列中全部条目
retrying —— 曾失败未达上限（retries > 0 且 < 3）：等待自动重试
failed   —— 已达上限（retries >= 3）：终态失败，需人工介入
```
`flush()` 返回的 `failed` 是**本轮结束时处于终态失败**的条目数，"刚失败一次"不算。

## 五、已知边界与后续

| 项 | 说明 |
|---|---|
| 冲突策略 | 本期"最后写入胜出"（PRD 明确 P2 再做手动选择） |
| 重放语义 | 若服务端已处理但响应丢失（超时），重放可能产生重复记录。真正幂等需服务端支持幂等键（`X-Idempotency-Key`），列入后续 |
| 队列容量 | 未设上限；正常使用（弱网几条）无风险，若担心可加"最多 500 条"策略 |
| 覆盖范围 | 拦截所有写方法（POST/PATCH/PUT/DELETE），不止 PRD 列的四个子模块——范围更大但要留意"某些写操作其实不该排队"的场景（目前没有） |
| 面板入口 | 在桌面端顶栏与移动端顶部均可点（角标仅在有队列时出现） |
