### ⚠️ 重要环境限制：本工作区**无法创建 git 分支**

实测（2026-09-16）：`git checkout -b` 与 `git branch` 都返回成功，但
**ref 文件不会被写入**（`.git/refs/heads/feature/` 目录始终为空）。

后果：HEAD 会指向一个不存在的 ref，git 随即把整个仓库视为
「尚无任何提交的新仓库」，`git status` 显示**所有文件都是 `A`（新增）**。

**如何识别自己踩到了它**：

```bash
git branch --show-current          # 输出了分支名
git rev-parse HEAD                 # fatal: ambiguous argument 'HEAD'
git status --short | head          # 大量 A 开头
```

**如何恢复**（不会动工作区与索引，安全）：

```bash
git symbolic-ref HEAD refs/heads/main
git status --short                 # 应恢复为正常的三四十条以内
```

**因此本期的做法是：直接在 `main` 上按语义化提交**（每个提交独立成事、
可单独 revert），而不是一任务一分支。若你需要在真正的分支上工作，请在
**IDE 或本地终端**（不受此沙箱限制）执行 `git switch -c <branch>`。

### 行尾符（2026-09-16 新增约定）

仓库已加 `.gitattributes`（`* text=auto eol=lf`）。**若编辑器把文件改成
CRLF，会立刻表现为「整个文件被重写」**。上次实测：

```
噪声：5839 插入 / 5297 删除      ← 26 个文件被改成 CRLF
真实： 792 插入 /  250 删除      ← 还原 LF 后
```

**如果 `git diff --stat` 出现整文件级变化而你的实际改动很小，先查行尾符。**
（注：加了 `.gitattributes` 后 git 会在入库时自动归一为 LF，所以提交是干净的；
但输出里会出现 `CRLF will be replaced by LF` 的提示，那是无害的。）

`logging.config.fileConfig()` 用系统 locale 编码读取 ini（zh-CN Windows 上是
GBK），**中文注释会直接抛 `UnicodeDecodeError` 导致迁移无法启动**。
该文件保持 ASCII-only。

### 3.3 W1 期间额外发现并修复的问题（计划外）

#### 问题 D · 「分支数据隔离」在 alembic CLI 路径下**完全失效**（严重）

《分支开发指南》推荐用 `VENUSTECH_DATA_DIR` 隔离分支数据库。实测发现
**同一件事存在两个真相来源**：

| 路径 | 连接串来源 | `VENUSTECH_DATA_DIR` |
|---|---|---|
| 后端启动自动迁移（`app/migrate.py`） | `cfg.set_main_option(..., get_settings().db_url)` | ✅ 生效 |
| 手动 `alembic upgrade head` | `alembic.ini` 里写死的 URL | ❌ **被无视** |

**实测证据**：设 `VENUSTECH_DATA_DIR=./data-s6test` 执行迁移后，
`data-s6test` 目录**未被创建**，而主库 `data/app.db` 被升级到了 0012。

**危害**：开发者以为分支库已被隔离，但只要手动跑一次 alembic，schema 变更
就会**静默打到主库** —— 没有报错，直到发现数据被改。

**修复**：`migrations/env.py` 的连接串改从 `settings.db_url` 派生（唯一真相
来源），offline / online 两条路径都覆盖；`alembic.ini` 的 url 降级为占位符。

#### 问题 E · alembic.ini 写中文注释会让迁移直接起不来

`logging.config.fileConfig()` 用系统 locale 编码读取 ini（zh-CN Windows 为
GBK）→ 中文注释抛 `UnicodeDecodeError`。已改为 ASCII-only 并在文件头写明原因。

#### 问题 F · 本工作区无法创建 git 分支

见 §0 的「重要环境限制」。已在 W1 期间触发一次（HEAD 变成 unborn，
`git status` 显示全仓库为 `A`），已用 `git symbolic-ref` 安全恢复。

#### 问题 G · `BaseRepository.create()` 每次调用都 commit

批量落库 30~40 条任务会 commit 同样多次，既慢（SQLite 每事务一次 fsync）
又**破坏原子性**（中途失败留下"计划已建、任务只建一半"的中间态）。
已新增 `create_many()` 走单次提交。

### 3.4 S6-1 的关键技术决策（供后续阶段参考）

**① 用脚本提取数据，不手工转录**

`backend/scripts/extract_domain_lib.py`：括号匹配切片 → Node 求值 → JSON →
Python 源码，并**断言** 13 领域 / 52 单元 / 90 任务 / 90 条达标标准 /
25 条可重复练习与评估报告基线逐项一致。

理由：90 条中文长文本手工抄写必然错字、漏条，且**无法验证完整性**。
脚本化后输出 100% 忠实，且将来更新领域库可重跑。

**② 移植 JS 算法时必须显式对齐 `Math.round`**

本算法大量用舍入做天数/周数分配。`JS Math.round(2.5)=3` 而
`Python round(2.5)=2`（银行家舍入）。用错**不会报错**，只会让计划"看起来
差不多" —— 属最难事后发现的移植错误。已用 `js_round()` 显式对齐并实测确认差异。

**③ 刻意留白：不实现源实现里那个从未生效的过滤**

源 `buildUnitDefs` 按**单元级** `u.beginnerOnly` 过滤，但数据标在**任务级**
→ 条件恒为真，**该过滤从未生效过**。本模块保留 `beginner_only` 数据但不实现
过滤：源作者本意无法从代码推断，贸然实现等于发明未经证实的行为。

**④ 扩领域是纯数据操作**

`domain_lib.py` 是常量表。要加领域（如「自由职业者的客户管理」），改数据 +
同步提取器里的断言基线即可，**无需改任何代码** —— 这对应了之前对
"13 个领域偏学生/考证场景"的担忧。

### 5.3 ⚠️ 重要边界：只补字段，未启用软删除语义

**列齐备了，但没有消费者**：

- `BaseRepository.delete()` 仍是硬删除（`db.delete` + commit）
- 各 Repository 的自定义查询**不会**自动过滤 `deleted_at`

**为什么不同时改语义**（这是一个刻意的范围决策，不是遗漏）：

1. **改动面大且危险**：`base.py` 的 `list/count/paginate` 可以加过滤，
   但各 Repository 里还有大量**直接写 `select()` 的自定义查询**
   （如 `TaskRepository.list_user_tasks`），它们不会继承 base 的过滤。
   只改一半会造成"有的查询过滤、有的不过滤"的不一致 —— **那比现状更糟**。
2. **当前无任何消费方**：本地优先、无云端同步，软删除语义没有读者。

**语义落地推迟到 S6-3b（diff-sync 引擎）时一并做**，届时连同自定义查询
一起梳理，并有同步测试来验证。

### 5.4 W3 期间的两个坑

**L · PetConfig 不能加 `TimestampMixin`**
它自己显式定义了 `updated_at` 字段，再继承 Mixin 会导致同一列被声明
两次，SQLAlchemy 直接报错。批量改模型时必须把它单独拎出来（只加
`SoftDeleteMixin`）。

**M · SQLite 不能给有数据的表加 NOT NULL 列**
Mixin 里 `created_at/updated_at` 是 `nullable=False`，但 SQLite 对已有
数据的表加 NOT NULL 列会失败。做法是：按 nullable 加入 → 再把 NULL
回填为迁移时刻。历史数据拿到的是近似值（数据库此前并未记录，无法还原）。

### A1 · 成长页（补 W2 的「看不见」）

S6-2 的 EXP 结算、等级、技能树自动归类全部跑通了，但用户能看到的只有顶栏
一个静态徽章。新增 `views/Growth/GrowthView.vue`（路由 `/growth`，hidden，
仅从顶栏徽章进入）：等级进度 + EXP 流水 + 22 类技能树 + 升级规则说明。
AppHeader 的徽章由 `<div>` 改为 `<button>` 并绑定跳转。

### A2 · 系统与诊断面板（四个后端模块没有界面）

加密状态 / 日志 / 事件总线 / 插件这四个模块**路由一直都在**，但前端既没封装
也没有入口 —— 想看一眼事件总线里跑了什么，只能去翻 SQLite 或日志文件。
新增 `api/system.ts` + 设置页「系统与诊断」面板。只做接入，未新增后端能力。

### A3 · 通知开关落库（把假开关变成真的）

设置页的 4 个通知开关（任务/复盘/系统/提示音）**是假的**：只是前端 `ref()`，
刷新即回默认值。后端 `settings` 表（PRD §15.11）从一期就建好了，却没有
repository、没有 service、没有路由 —— 一张彻底的死表。

按四层分层补齐完整链路 `repositories/settings_repo.py` → `services/settings_service.py`
→ `api/settings.py`，并给前端加 `api/settings.ts`。

三个值得记住的设计点：

1. **upsert 而非 insert** —— `settings` 是 `(user_id, key)` 唯一，重复保存会
   撞约束，所以写入语义收敛在 Repository 层（含软删除行复活）；
2. **键白名单** —— 只允许已登记的键落库，防止前端误传把配置表写脏；
3. **BaseSwitch 补 `change` 事件** —— 此前只发 `update:modelValue`，消费方无法
   区分「用户点了」和「程序赋值」，被迫用 `watch` 猜测。

冒烟 **58 → 63**（+5）：默认值、写入生效、upsert 幂等、白名单拒绝、持久化重读。

### 踩坑记录：并行编辑同一文件会丢改动

本轮用两条并行编辑同时改 `SettingsView.vue`（一条改 import、一条插入逻辑块），
工具都返回成功，但**后写的一条覆盖了前一条**，导致 `vue-tsc` 报「settingsApi
已声明但未使用」+「loadNotifySettings 找不到」。同一文件 `backend/app/api/__init__.py`
也中招（import 行的 `settings,` 丢失 → 后端冒烟 `NameError`）。

**结论：同一文件的多处改动必须串行编辑；并行只用于不同文件。**
