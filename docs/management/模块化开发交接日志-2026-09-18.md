## 三、开发硬约束（必须遵守）

### 3.1 分支工作流
```
1. 开工：git checkout main && git pull → git checkout mod-xxx
2. 开发：小步提交（Conventional Commits：feat(mod-xxx): …）
3. 验收：python scripts/check_all.py
        python scripts/audit_hardcoded_colors.py
4. 合并：git checkout main && git merge --no-ff mod-xxx
5. 推送：git push origin main && git push origin mod-xxx
```

**注意：**
- 分支名用单级 `mod-xxx`，不要用 `feature/xxx`
- 一次只有一个智能体动一个分支
- 合并用 `--no-ff`，保留模块边界
- 分支不过周，完成即合并即删除

### 3.2 代码规范
1. **设计令牌唯一来源**：`frontend/src/styles/variables.scss`，组件内不允许hex色值
2. **组件全自研**：不引入Element Plus全量，基础组件在 `src/components/common/`
3. **六维导航不可改结构**：维度与二级Tab在 `constants/dimensions.ts`，路由在 `src/app/router/index.ts`
4. **数据流**：Views → Composables → API层，API层是后端唯一入口
5. **新增模型必带** `updated_at` / `deleted_at`（架构守护会拦）
6. **移动端适配**：靠 `<768px` 媒体查询，全局兜底层已在 `global.scss`

### 3.3 不碰的东西
- 不要自动操作git（提交和推送由工程侧统一处理）
- 不要修改其他模块的文件（跨模块改动落到 `mod-platform`）
- 不要在仓库目录建测试SQLite数据库（用 `%TEMP%`）

## 四、建议开发顺序

按依赖关系和风险排序：

| 顺序 | 模块 | 理由 |
|------|------|------|
| 1 | **mod-platform** | 基础设施先行，密钥轮换/插件权限影响所有模块 |
| 2 | **mod-dashboard** | 首页是门面，性能优化立竿见影 |
| 3 | **mod-execution** | 任务四象限是核心功能缺口 |
| 4 | **mod-companion** | 第二分身是差异化亮点，流式输出+长期记忆 |
| 5 | **mod-life** | 三期核心，身份轴深化 |
| 6 | **mod-knowledge** | 编辑器升级工作量大，可并行 |
| 7 | **mod-asset** | 学习算法调优为主 |
| 8 | **mod-tools** | 离线队列是移动端重点 |
