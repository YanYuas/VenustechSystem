# 移动端部署 + DeepSeek 语音行程助理方案

> 2026-09-17 · 衍煜提出 · 状态：待拍板
> 需求原话：手机端通过语音转文字发给 DeepSeek API，把要办的事情、条件、对象、
> 截止时间说清楚后，AI 整理成行程，通过面板查看待办。

---

## 一、结论先行

| 决策点 | 推荐方案 | 一句话理由 |
|---|---|---|
| 移动端形态 | **PWA（响应式 Web 应用）** | 零打包成本，手机浏览器"添加到主屏幕"即装；后端零改动 |
| 访问通道 | **局域网直连 + Tailscale（外网可选）** | 数据主权铁律：SQLite 不出你的机器，不暴露公网 |
| 语音输入 | **Web Speech API（浏览器原生 STT）** | 免费免 Key；iOS Safari / Android Chrome 都支持；不支持时降级文本框 |
| AI 解析 | **DeepSeek（OpenAI 兼容协议）** | 便宜、国内直连、JSON Mode 输出稳定 |
| AI 权限边界 | **AI 只产"建议"，人确认才落库** | 对齐系统铁律"终端只做白名单动作"——AI 永远不直接写业务表 |
| 数据落点 | **复用 tasks / reminders，零新表** | 行程就是待办，别为语音再发明一套存储 |

## 二、为什么是 PWA 而不是打包 App

| 维度 | PWA（推荐） | Capacitor 打包 | 原生开发 |
|---|---|---|---|
| 工作量 | 0.5 天（manifest + 图标 + 视口） | 2–3 天 + Android 证书 | 周级 |
| 更新 | 刷新即最新（和 PC 同源） | 要重新打包分发 | 同左 |
| 语音 API | ✅ Web Speech API | ✅（WebView 内需配置） | ✅ |
| 离线 | 有限（SW 缓存壳） | 好 | 好 |
| 上架 | 不需要 | 侧载/APK 直装 | 应用市场 |

**修订（2026-09-17 下午，衍煜拍板后的网络与形态补充）**：
电脑固定寝室网，手机在校园网/流量 —— 跨网访问是硬需求，**打包 App 有必要**。
本文原"不选打包"的立场作废，修订为：**PWA 先行验证 + Capacitor 壳正式化**，
两者共用同一套前端代码，语音层做双通道适配（见 §4.6）。

### 2.1 网络方案（跨网怎么连回寝室的电脑）

**首选：Tailscale（免费档足够，两台设备各装一个即成）**

```
手机（校园网/流量）──┐
                      ├── Tailscale 加密虚拟局域网（WireGuard）──> PC（寝室网，100.x.y.z）
手机（室友热点）  ──┘
```

- 手机**无论在哪个网络**，都访问同一个地址 `http://<PC的tailscale IP>:3000`
- 不暴露公网、不需要公网 IP、不需要域名证书、不需要内网穿透服务商
- 寝室 NAT 不是问题：Tailscale 全 outbound 连接，校园网防火墙一般不拦
- ** mainland 劣势要知道**：直连打洞失败时走官方 DERP 中继（境外），可能慢
  （1–3 秒延迟，AI 解析场景可接受）；不能忍时自建国内 DERP 节点（VPS 一台即可）
- 备选对比：frp+VPS（要买服务器+暴露端口，弃）、ZeroTier（同类，moon 可自建，弃——
  Tailscale 体验更好）、花生壳（实名+限速，弃）

**PC 侧要求**：电脑保持开机不休眠（电源设置关睡眠；可选 BIOS 来电自启 +
Waker 断网唤醒）。大脑永远在 PC 上，这一点不因为打包 App 而改变。

### 2.2 App 形态：Capacitor 壳（同代码，两个发行通道）

```
frontend（Vue 源码，唯一）
 ├─ Web 构建 → PWA（浏览器/添加主屏）      —— 免安装兜底
 └─ Capacitor 构建 → Android APK           —— 正式 App（独立图标/入口/全屏）
```

- **壳里不打包后端**：App 是客户端，API 地址指向 PC 的 Tailscale IP（`http://100.x.y.z:3000`）。
  数据主权铁律不破：SQLite 只有一份，在电脑上
- AndroidManifest 开 `usesCleartextTraffic`（仅限 tailscale 网段；HTTP 无证书，
  流量本身在 WireGuard 隧道内加密，实际安全性足够）
- CORS：`settings.cors_origins` 加 `capacitor://localhost`（Capacitor 的 origin）
- **iOS 不做壳**（签名麻烦），iPhone 场景用 PWA + Tailscale 即可

**"独立个体"的诚实边界**：App 有独立图标、独立全屏体验、原生语音（见 §4.6）、
可加本地通知推送；但数据大脑在 PC —— **电脑关机时 App 只能看缓存**。
v1 不做移动端离线库；若将来要"电脑关机也能记"，走 M5：离线暂存队列
（语音文本存手机本地，联网后 flush 给 PC），成本约 0.5 天。

### 2.3 语音 API 的双通道（打包后 WebView 的坑）

**Android WebView 不支持 Web Speech API 的 SpeechRecognition** —— 直接打包会把
语音功能搞坏。解法：壳内用 Capacitor 原生插件 `@capacitor-community/speech-recognition`
（走系统原生 STT，体验反而比浏览器好）。

```ts
// 语音适配层（前端唯一入口，双通道自动选择）
async function speechToText(): Promise<string> {
  if (Capacitor.isNativePlatform()) {
    return nativeSpeechPlugin.listen({ language: 'zh-CN' })   // App 内：原生 STT
  }
  return webSpeechRecognition('zh-CN')                        // 浏览器/PWA：Web Speech API
}
```

PWA 和 App 共用同一个 `/assistant` 页面代码，语音层按运行环境自动切换。

## 三、系统架构（改动量标注）

```
手机浏览器（PWA）
 ├─ 语音按钮 → Web Speech API（浏览器内完成 语音→文字，免 Key）
 ├─ 文字 → POST /api/v1/assistant/parse          【新增】
 ├─ AI 建议 → 确认面板（可编辑/删改）             【新增】
 └─ 确认 → POST /api/v1/assistant/apply          【新增，白名单动作】

PC 后端（FastAPI，唯一写入点）
 ├─ assistant_service.parse(text)                【新增 service】
 │   ├─ 有 Key → DeepSeek chat（JSON Mode）
 │   └─ 无 Key → 本地规则解析（正则时间词，降级）
 ├─ apply(items) → TaskService / ReminderService 【复用，零新表】
 └─ DeepSeek Key → settings 表加密存储           【复用 encryption】

SQLite（WAL，唯一数据源）
```

**改动面**：新增 1 个 API 模块 + 1 个 service + 前端 1 个页面；复用一切现有设施
（鉴权、响应封套、事件总线→EXP 结算、身份轴、冒烟框架）。

## 四、DeepSeek 集成设计

### 4.1 连接参数

- 协议：OpenAI 兼容（`https://api.deepseek.com/v1/chat/completions`）
- 模型：`deepseek-chat`（便宜，解析任务足够；V3 也行）
- `response_format: {"type": "json_object"}` + `temperature: 0.2` —— 输出稳定可解析
- 超时 15s，失败重试 1 次，再失败降级本地规则解析

### 4.2 Key 管理（安全）

- Key 存 `settings` 表：`assistant.deepseek_key`，**写库前用现有 encryption 模块加密**
- 前端永远只见 `已配置/未配置`，永不回显明文
- 设置页 AI 配置区加输入框（复用现有 AI Key 的交互模式）

### 4.3 解析提示词（system prompt 草案）

```
你是个人行程助理。用户会用口语描述一堆要做的事。把它拆解成结构化条目。
只输出 JSON，格式：
{
  "items": [{
    "kind": "task" | "reminder" | "note",   // task=要做的事, reminder=时间点提醒, note=备忘
    "title": "简短标题（10字内）",
    "deadline": "2026-09-20T15:00:00" | null, // 尽量推断具体时间；只有日期给 T00:00
    "people": ["老师"],                        // 涉及对象
    "location": null,                          // 地点
    "priority": "high" | "medium" | "low",    // 有截止时间默认 high
    "notes": "原始描述里的补充条件"
  }],
  "clarifications": ["用户没说清、值得问一句的点"]
}
规则：
- 今天是 {now}；"明天/周五/下周三"按此推算具体日期
- 一句话里多个事拆成多条；寒暄/无关内容直接丢弃
- 宁可标 null 也不猜；拿不准的放进 clarifications
```

### 4.4 无 Key 降级（复用既有降级哲学）

正则解析：时间词表（今天/明天/后天/周X/下月X号/下午X点/X点半）+ "、"/"然后"/"还有"
切分条目 + 逗号前的对象词。准确率不高但可用 —— 保证**零配置也能用**，
和 AI 摘要/技能归类的降级策略一脉相承。

### 4.5 AI 权限边界（这条是铁律级）

- `parse` 只**返回建议 JSON**，不写任何表
- 前端确认面板展示建议 → 用户可改标题/时间/删除 → 点"全部加入"
- `POST /assistant/apply` 接收**用户确认后的**条目，逐条走 TaskService.create /
  ReminderService.create（正常校验、事件总线照常触发 EXP）
- 理由：语音口误、AI 幻觉都不该静默变成你的待办。人和 AI 的写入权限分离。

## 五、数据落点（零新表）

| AI 输出 | 落到哪 | 字段映射 |
|---|---|---|
| kind=task | `tasks` | title / due_date=deadline / notes / priority |
| kind=reminder | `reminders` | 提醒时间=deadline / 内容=title |
| kind=note | `inbox_items`（收集箱） | 原文入箱，不定时处理 |
| 身份归属 | tasks.identity_id | 面板上可选；AI 不猜身份（未归类即可，人可后挂） |

> 有意不做的：不为"行程"建新表、不做日历视图（现有任务列表按 due_date
> 排序已覆盖）。行程的本质就是带截止时间的任务。

## 六、移动端面板设计（`/assistant`，移动优先）

```
┌──────────────────────────┐
│  今天 · 9月17日 周四        │
│  ┌────────────────────┐  │
│  │ 🎤 按住说话…          │  │  ← Web Speech API，松手转文字
│  └────────────────────┘  │
│  （识别中：明天下午三点找老师谈开题，还要买高铁票…） │
│                          │
│  ▼ AI 整理出 2 条建议      │
│  ☑ [任务] 找老师谈开题     │
│     明天 15:00 · 对象:老师 │
│  ☑ [任务] 买高铁票         │
│     无截止 · 建议尽快      │
│  ❓ "开题的具体形式？"      │  ← clarifications
│  [ 全部加入待办 ]  [ 放弃 ] │
│──────────────────────────│
│  我的待办                  │
│  ⚠ 逾期（1）               │
│  今天（3）  明天（2）  之后  │
│  …任务卡片（滑动完成）      │
└──────────────────────────┘
```

- 语音按钮居底大目标（触控 ≥48px），单手可达
- 建议条目：复选框可踢掉不要的；标题/时间可就地改
- 待办分组：逾期 / 今天 / 明天 / 之后 —— 就是现有任务列表的移动布局
- PWA manifest：竖屏、主题色、桌面图标；`display: standalone` 后像原生 App

## 七、分期实施（每期带验收）

| 期 | 内容 | 工作量 | 验收 |
|---|---|---|---|
| **M1** | PWA 化：manifest + 图标 + 移动视口 + 触控尺寸审计；手机连局域网跑通全站 | 0.5d | 手机浏览器添加到主屏，核心页面可用 |
| **M2** | assistant 后端：DeepSeek 客户端 + Key 加密存储 + JSON 解析 + 无 Key 降级 + 单元冒烟 | 1d | 冒烟：mock DeepSeek 返回 → parse 出结构化；无 Key → 降级解析生效 |
| **M3** | 前端：语音按钮（双通道适配层）+ 建议确认面板 + apply 白名单端点 + 移动待办分组 | 1d | 冒烟：apply 走 TaskService 落库；前端 build 通过 |
| **M4** | Tailscale（两台设备组网）+ Capacitor 壳打包 APK（原生语音插件 + CORS/cleartext 配置） | 1d | 手机流量下打开 App，语音 → DeepSeek → 确认 → PC 落库全链路 |
| **M5（可选）** | 离线暂存队列：PC 不可达时语音文本存本地，联网后 flush | 0.5d | 断网录 3 条 → 联网后自动入待办 |

总计 **3.5 天（不含 M5）**，M2 是核心，其余都是薄壳。实施顺序
M1 → M2 → M3 → M4 不变；PWA 不是弯路——它就是 App 的同一份代码。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| **Android WebView 不支持 Web Speech API** | 语音适配层双通道：App 内用 Capacitor 原生语音插件，PWA 用 Web Speech API（§2.3） |
| 校园网拦截 Tailscale 打洞（UDP 限制） | 自动回落官方 DERP 中继（能通但慢）；长期方案自建国内 DERP 节点 |
| PC 关机时 App 不可用 | 电源设置关睡眠保持在线；M5 离线暂存队列兜底"断网也能记" |
| DeepSeek 输出 JSON 不合法 | JSON Mode + 温度 0.2 + 解析失败重试 1 次 → 仍失败走本地降级，前端提示"已用简化解析" |
| 手机/PC 同时写 SQLite | WAL 已开，个人规模读写比完全够；同步引擎（S6-3b）天然兜底多端 |
| Key 泄漏 | 加密落库 + 永不回显前端 + 不进日志；App 内不发 Key（解析在 PC 后端） |
| 语音口误生成错误待办 | 确认流（人审后才落库）从机制上杜绝 |
| HTTP 明文（无证书） | 流量在 WireGuard 隧道内加密，实际安全性足够；Android 侧仅对 tailscale 网段放行 cleartext |

## 九、与既有铁律的对账

- ✅ 四层分层：assistant 模块 api→service，复用 TaskService/ReminderService 落库
- ✅ AI 永不直接写业务表：apply 白名单动作，人确认
- ✅ 数据主权：PWA+Tailscale，SQLite 不出机器；同步包（S6-3b）本就支持
- ✅ 零配置可用：无 Key 降级规则解析
- ✅ 设计令牌：新页面全部走 token，颜色审计零新增
- ✅ 文档驱动：本方案即文档，实施后回填三期推进日志
