# ADR-0001 采用「分层模块化单体」，不做微服务，也不做一次性垂直切片

- 状态：**已采纳**（2026-10-26）
- 决策者：架构重整（2026-10）
- 相关：[ARCHITECTURE.md](../../../ARCHITECTURE.md) §4、§5、§11

## 背景

现状是 33 个 API 模块、25 个 service、29 个 repository、25 个 model，全部按**层**平铺
（`api/`、`services/`、`repositories/`、`models/`），命名严格遵循 `<module>` 前缀，
即「域前缀 + 层后缀」。

2026-10 架构审计的实测结论：

- 分层方向**基本健康**：repositories 零上行依赖、无真实循环、services 零 FastAPI 依赖。
- 但**层收益未兑现**：service 9441 行 vs repository 1412 行；16/31 个 service 绕过
  repository 直接操作 ORM；4 个 service 完全没有 repository。
- 真正的耦合中心是 `identity_repo`（12 个消费者）、`task_repo`（8）、`document_repo`（6）
  这类**跨域数据访问**，而不是目录结构本身。

## 决策

1. **目录结构继续按层**（`api/services/repositories/models/schemas`），不整体改为
   `modules/<domain>/{...}` 垂直切片。
2. **领域边界用机器可读注册表表达**（`docs/architecture/domains.json`）+ AST 守护强制，
   而不是靠目录嵌套。
3. 真正的收口点在 **Phase 2**：事务边界上移、Repository 收口、跨域只走 service 公开接口。

## 理由

- 一次移动约 160 个文件 + 全部 import 路径，收益是"看起来更领域化"，成本是整仓回归风险；
  而领域收益（改一处不炸别处）来自**边界收口**，不来自目录名。
- 命名已经是稳定的一域一文件映射，`domains.json` 已能让人和机器都准确定位模块归属。
- 当前最痛的三件事（事务原子性、迁移基线、备份导入 422）都**不是**目录结构造成的，
  先做结构搬迁会掩盖它们。

## 后果

- ✅ 变更成本低、可逆、CI 可持续验证。
- ⚠️ 新增模块仍需动 5 个目录 → 用 `domains.json` 登记 + §8 的 12 步清单 + 守护兜底。
- 📌 **重新评估触发条件**：模块数 >50、或出现第二名长期开发者、或单文件超 2000 行成为
  常态时，再考虑按领域分包（届时可保留 `api/` 作为 shim 分批迁移）。

## 替代方案

- **微服务**：单机单用户、本地优先，拆进程只增加部署与调试成本。否决。
- **一次性垂直切片**：回归风险与收益不成比例，且无自动化 UI 回归网兜底。本轮否决，Phase 2 试点。
- **只写文档不改代码**：审计已证明"文本规则守护"抓不到真实违规，故同时落地 AST 守护。
