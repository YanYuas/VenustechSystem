#### ADR-001：桌面应用容器选型

**问题**：本地桌面应用用什么技术容器？

| 选项 | 优势 | 劣势 |
|------|------|------|
| **Electron** | 生态成熟、Node.js原生、调试工具完善、自动更新方案现成、你已熟悉Web技术 | 包体大（~150MB）、内存占用高 |
| Tauri | 包体小（~10MB）、内存低、Rust性能好 | Rust学习成本高、AI/插件生态弱、Windows透明窗口兼容性问题多 |
| Wails | Go后端、包体中等 | 生态不成熟、前端能力受限 |
| 原生WinUI/WPF | 性能最优、原生体验 | 开发效率极低、与Vue3技术栈不兼容 |

**决策**：Electron（最新LTS版本）

**理由**：
1. 你已熟悉Vue3+Node技术栈，Electron学习成本趋近于零
2. 桌宠需要透明窗口+帧动画+系统托盘+全局快捷键，Electron的BrowserWindow API完全覆盖
3. 二期需要插件系统（Python/JS脚本），Electron的child_process和Node生态是天然优势
4. Tauri的Rust侧开发会成为单人开发的瓶颈，且透明窗口在Windows上有已知bug

**后果**：
- 安装包约150-200MB，可接受（Obsidian约100MB，VS Code约90MB）
- 空闲内存约200-300MB，需通过进程管理优化
- 需注意Electron安全配置（contextIsolation、nodeIntegration禁用）

#### ADR-002：后端进程架构

**问题**：FastAPI后端以什么形式运行？

| 选项 | 说明 |
|------|------|
| **独立子进程** | Electron主进程spawn Python子进程，运行FastAPI(Uvicorn)，通过HTTP通信 |
| 内嵌Python解释器 | 用python-shell或类似库在Node进程内执行Python |
| 纯Node后端 | 不用Python，全部用Node.js实现后端逻辑 |

**决策**：独立子进程（FastAPI + Uvicorn）

**理由**：
1. 你已熟悉FastAPI+Python，AI生态（OpenAI SDK、后续本地模型Ollama对接）Python最成熟
2. 独立进程崩溃不影响前端，可自动重启（容错隔离）
3. HTTP通信是标准协议，后续如果要做云端版本，后端代码几乎零修改
4. 内嵌解释器调试困难，版本管理复杂

**后果**：
- 需管理Python运行时（打包内嵌Python解释器或检测系统Python）
- 进程间通过HTTP（127.0.0.1随机端口）通信，需处理端口冲突
- 应用退出时需确保子进程正确终止（孤儿进程问题）

#### ADR-003：本地数据库选型

**问题**：本地数据存储用什么？

| 选项 | 优势 | 劣势 |
|------|------|------|
| **SQLite** | 零配置、单文件、事务ACID、Python/Vue双端生态好 | 并发写入受限（写锁）、无JSONB原生类型 |
| 纯文件系统（Markdown） | 开放性最高、用户可直接编辑 | 查询/关联/事务弱、需自建索引 |
| IndexedDB（浏览器端） | 前端原生、异步 | 后端无法访问、数据导出复杂、Electron重启可能丢失 |
| LowDB/NeDB | 简单JSON文件 | 大数据量性能差、无事务 |

**决策**：SQLite（WAL模式）+ 文件系统混合

**理由**：
1. SQLite是经过20年验证的嵌入式数据库，ACID事务保证数据不丢
2. WAL模式下读写并发性能足够个人工具使用
3. 结构化数据（任务/对话/配置）存SQLite，文档内容同时写Markdown文件（开放性）
4. 后续二期要做同步盘同步，SQLite的WAL文件+文件系统组合最容易处理

**后果**：
- 需处理SQLite的写锁（所有写操作串行化，用单例连接+队列）
- JSON字段用TEXT存储，应用层序列化/反序列化
- 数组类型用逗号分隔字符串或JSON数组实现
- 需定期VACUUM和WAL checkpoint（防止WAL文件无限增长）

#### ADR-004：前端状态管理

**问题**：Vue3应用的状态管理方案？

| 选项 | 说明 |
|------|------|
| **Pinia** | Vue官方推荐，TS友好，轻量 |
| Vuex 4 | 旧方案，较繁琐 |

**决策**：Pinia，按业务域划分store

**理由**：Pinia是Vue3官方推荐，TS支持好，API简洁，devtools支持完善。

**后果**：需合理划分store，避免单个store过大。

#### ADR-005：富文本编辑器

**问题**：文档编辑器用什么？

| 选项 | 优势 | 劣势 |
|------|------|------|
| **Tiptap** | 基于ProseMirror、模块化、Vue3支持好、可扩展 | 学习曲线、包体积较大 |
| Milkdown | 更轻量、Markdown优先 | 生态不如Tiptap |
| CodeMirror 6（Markdown源码） | 极轻量、性能好 | 非所见即所得，用户体验差 |
| Quill | 简单易用 | 扩展能力弱、维护不活跃 |

**决策**：Tiptap 2.x

**理由**：PRD要求表格/图片/任务列表/代码块等功能，Tiptap的扩展生态最完善，且输出JSON结构便于AI处理和版本管理。

**后果**：包体积约200KB（gzip后约60KB），可接受。需自定义扩展实现[[]]双向链接语法。

#### ADR-006：AI流式通信

**问题**：前端如何接收AI流式响应？

| 选项 | 说明 |
|------|------|
| **fetch + ReadableStream** | 标准API，支持POST body，灵活 | 需手动处理SSE解析 |
| EventSource | 浏览器原生SSE支持 | 只支持GET，无法传body |
| WebSocket | 全双工 | 后端需维护WS连接，过度设计 |

**决策**：fetch + ReadableStream

**理由**：发送消息需要传body（内容+引用文档ID），EventSource的GET限制不适用。fetch流式读取是标准方案。

#### ADR-007：API Key加密存储

**问题**：用户的DeepSeek API Key存在哪？怎么加密？

| 选项 | 说明 |
|------|------|
| **Windows DPAPI** | 系统级加密，密钥绑定用户账户，无需用户记密码 | 仅Windows |
| 自定义AES加密 | 跨平台，需用户主密码 | 用户可能忘记主密码=Key丢失 |
| 明文存配置文件 | 最简单 | 安全隐患，恶意软件可读取 |

**决策**：Windows DPAPI（通过node-nodevices或python-cryptography+win32crypt）

**理由**：一期仅Windows，DPAPI是最安全且用户无感的方案。API Key绑定Windows用户账户，其他用户/恶意程序无法解密。

**后果**：二期跨平台（macOS）时需适配Keychain。需处理DPAPI解密失败的情况（用户账户变更）。

### 1.2 架构原则

1. **进程隔离**：前端渲染进程、Electron主进程、Python后端进程三者隔离，单一崩溃不影响全局
2. **本地优先**：所有核心功能不依赖网络，AI功能优雅降级
3. **数据所有权**：用户数据全部明文可查（Markdown文件），数据库可导出为SQL
4. **可测试性**：业务逻辑与UI框架解耦，核心算法可独立单元测试
5. **渐进增强**：一期最简实现，架构预留二期扩展点（本地模型、插件、云端同步）
6. **安全默认**：Electron安全配置默认最严格，API Key加密存储

## 第二章：进程架构与通信

### 2.1 三进程模型

```
┌─────────────────────────────────────────────────────────┐
│                   Electron 应用                          │
│                                                         │
│  ┌──────────────┐    IPC     ┌──────────────────┐      │
│  │ 主进程        │◄─────────►│ 渲染进程           │      │
│  │ (Main)       │            │ (Renderer/Vue3)   │      │
│  │              │            │                   │      │
│  │ - 窗口管理    │   HTTP     │ - UI界面          │      │
│  │ - 桌宠窗口    │◄─────────►│ - 状态管理        │      │
│  │ - 系统托盘    │  127.0.0.1 │ - API调用         │      │
│  │ - 全局快捷键  │   :port    │ - 用户交互        │      │
│  │ - 子进程管理  │            │                   │      │
│  └──────┬───────┘            └───────────────────┘      │
│         │ spawn/terminate                               │
│         ▼                                               │
│  ┌──────────────┐                                       │
│  │ Python子进程  │                                       │
│  │ (FastAPI)    │                                       │
│  │              │                                       │
│  │ - REST API   │                                       │
│  │ - 业务逻辑    │                                       │
│  │ - SQLite     │                                       │
│  │ - AI调用      │                                       │
│  │ - 文件操作    │                                       │
│  └──────────────┘                                       │
└─────────────────────────────────────────────────────────┘
```

### 2.2 进程职责划分

| 进程 | 职责 | 禁止 |
|------|------|------|
| **主进程** | 窗口创建/管理、桌宠、系统托盘、全局快捷键、Python子进程生命周期、自动更新、原生API调用 | 不执行业务逻辑、不直接操作数据库 |
| **渲染进程** | Vue3 UI渲染、用户交互、状态管理、API调用、前端计算 | 不直接访问文件系统、不调用Node原生API（通过preload桥接） |
| **Python子进程** | REST API、业务逻辑、数据库操作、AI调用、文件读写、定时任务 | 不操作UI、不管理窗口 |

### 2.3 通信机制

#### 2.3.1 主进程 ↔ 渲染进程（IPC）

使用Electron的`contextBridge` + `ipcRenderer`/`ipcMain`，通过preload脚本暴露有限API。

**preload.ts 暴露的API白名单**：
```typescript
interface WindowAPI {
  // 窗口控制
  window: {
    minimize: () => void;
    maximize: () => void;
    close: () => void;
    setAlwaysOnTop: (flag: boolean) => void;
  };
  // 桌宠
  pet: {
    show: () => void;
    hide: () => void;
    setPosition: (x: number, y: number) => void;
    getPosition: () => { x: number; y: number };
    onAction: (callback: (action: string) => void) => void;
  };
  // 系统
  system: {
    getBackendPort: () => number;
    openExternal: (url: string) => void;
    openPath: (path: string) => void;
    getDataDir: () => string;
  };
  // 全局快捷键
  shortcuts: {
    register: (accelerator: string, callback: () => void) => void;
    unregister: (accelerator: string) => void;
  };
}
```

**安全规则**：
- `contextIsolation: true`（强制）
- `nodeIntegration: false`（强制）
- `sandbox: true`（渲染进程沙箱）
- preload只暴露白名单API，不暴露完整Node API
- IPC消息做参数校验，防止恶意注入

#### 2.3.2 渲染进程 ↔ Python后端（HTTP）

- 后端启动时绑定`127.0.0.1`随机端口（避免冲突），将端口写入临时文件或通过IPC通知主进程
- 渲染进程通过Axios调用`http://127.0.0.1:{port}/api/v1/*`
- 流式接口（AI对话）用`fetch + ReadableStream`
- 所有请求超时30秒（AI流式接口超时60秒）

**端口分配机制**：
1. 主进程启动时生成随机端口（30000-40000范围）
2. 通过环境变量`VENUSTECH_PORT`传给Python子进程
3. Python子进程启动后绑定该端口
4. 主进程等待后端健康检查（`GET /api/v1/health`）通过后，通知渲染进程
5. 渲染进程从`window.system.getBackendPort()`获取端口

#### 2.3.3 主进程 ↔ Python子进程

- 主进程通过`child_process.spawn()`启动Python
- 通过stdout/stderr捕获后端日志
- 后端异常退出时，主进程监听`exit`事件，自动重启（最多3次，间隔5秒）
- 应用退出时，主进程发送SIGTERM给Python，等待5秒后强制kill

### 2.4 启动时序

```
T0: 用户双击应用
T0+0ms: Electron主进程启动
T0+50ms: 主进程读取配置，分配随机端口
T0+100ms: 主进程spawn Python子进程（传端口）
T0+150ms: 主进程创建主窗口（显示加载动画）
T0+200ms: 渲染进程加载Vue应用（显示启动页）
T0+500ms: Python子进程初始化（导入依赖）
T0+1500ms: FastAPI启动完成，监听端口
T0+1600ms: 主进程健康检查通过，通知渲染进程
T0+1700ms: 渲染进程请求/dashboard数据
T0+2000ms: 首页渲染完成，加载动画消失
T0+2100ms: 桌宠窗口创建并显示
目标: 冷启动 ≤ 5秒（低端机），≤ 3秒（主流配置）
```

### 2.5 退出时序

```
用户点击关闭
  → 主进程收到close事件
  → 通知渲染进程保存未保存数据（文档自动保存）
  → 渲染进程完成保存后回执
  → 主进程发送SIGTERM给Python子进程
  → 等待Python退出（最多5秒）
  → 超时则SIGKILL
  → 关闭所有窗口（主窗口+桌宠）
  → 应用退出
```

### 3.2 依赖注入

```python

    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

def get_task_service(db: Session = Depends(get_db)):
```

**评估员视角挑剔点**：

### 3.3 统一响应与异常处理

**统一响应格式**：
```python
# core/response.py
class APIResponse(BaseModel):
    code: int = 0
    message: str = "success"
    data: Any = None
    timestamp: int = Field(default_factory=lambda: int(time.time()))

def success(data=None, message="success"):
    return APIResponse(data=data, message=message)

def error(code: int, message: str):
    return APIResponse(code=code, message=message)
```

**异常体系**：
```
AppException（基类，含code/message/http_status）
├── ValidationException (code=1001, http=400)
├── NotFoundException (code=1002, http=404)
├── BusinessException (code=3001, http=409)
│   ├── TaskStateException（非法状态流转）
│   ├── FocusTaskExistsException（已有今日最重要任务）

│   └── AIStreamInterrupted
└── ServerException (code=5000, http=500)
```

**全局异常处理器**：
```python
@app.exception_handler(AppException)
async def app_exception_handler(request, exc):
    logger.error(f"API异常: {exc.code} - {exc.message}")
    return JSONResponse(status_code=exc.http_status, content=error(exc.code, exc.message).dict())

@app.exception_handler(Exception)
async def unhandled_exception_handler(request, exc):
    logger.exception("未捕获异常")
    return JSONResponse(status_code=500, content=error(5000, "服务器内部错误").dict())
```

**评估员视角**：所有异常必须有明确的错误码，前端根据错误码做对应处理（如AIKeyMissing→引导去设置页），禁止前端直接显示后端异常堆栈。

### 3.4 事件总线（模块解耦）

模块间通过事件总线通信，避免直接依赖：

```python
# core/event_bus.py
class EventBus:
    _handlers: dict[str, list[Callable]] = {}

    @classmethod
    def subscribe(cls, event: str, handler: Callable):
        cls._handlers.setdefault(event, []).append(handler)

    @classmethod
    def publish(cls, event: str, **kwargs):
        for handler in cls._handlers.get(event, []):
            try:
                handler(**kwargs)
            except Exception:
                logger.exception(f"事件处理失败: {event}")

# 事件定义
EVENTS = {
    "task.completed": "任务完成",
    "task.created": "任务创建",
    "document.saved": "文档保存",
    "document.saved": "触发AI摘要+标签（异步）",
    "review.generated": "复盘生成",
}
```

**典型场景**：文档保存后触发AI摘要生成——document_service发布`document.saved`事件，ai_worker订阅并异步处理，两者完全解耦。

### 3.5 异步任务处理

AI调用（摘要/标签/灵感/反思问题）是耗时操作，不能阻塞HTTP响应。

**方案**：FastAPI的`BackgroundTasks` + 事件总线

```python
# api/document.py
@router.post("/documents")
async def create_document(doc: DocumentCreate, background_tasks: BackgroundTasks):
    result = document_service.create(doc)
    # 异步触发AI处理（不阻塞响应）
    background_tasks.add_task(
        event_bus.publish, "document.saved", document_id=result.id
    )
    return success(result)
```

**评估员挑剔点**：
- BackgroundTasks在请求响应后执行，但如果应用退出会丢失（一期可接受，二期换APScheduler）
- AI任务需做幂等处理（同一文档重复保存不重复生成）
- AI任务失败需记录日志，不影响主流程

### 3.6 并发控制（SQLite写锁）

SQLite的写锁是数据库级的，并发写入会报`database is locked`。

**解决方案**：
1. **WAL模式**：读写不互斥，写写仍互斥
2. **超时设置**：`PRAGMA busy_timeout=5000`（等待5秒而不是立即报错）
3. **单例连接**：整个应用用一个数据库连接（SQLite连接不是线程安全的，用线程局部存储或队列）
4. **写操作串行化**：所有写操作通过一个异步队列执行

```python
# database.py
engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,  # 单连接池
)

# 连接时执行PRAGMA
@event.listens_for(engine, "connect")
def set_sqlite_pragma(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL")
    cursor.execute("PRAGMA busy_timeout=5000")
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.execute("PRAGMA cache_size=-20000")  # 20MB缓存
    cursor.close()
```

**评估员视角**：单用户场景下并发写入极少（用户操作是串行的），唯一的并发来源是后台AI任务。WAL+busy_timeout已足够，不需要引入复杂的写队列。

## 第五章：数据层深度设计

### 5.1 SQLite配置与调优

**核心PRAGMA**：
```sql
PRAGMA journal_mode=WAL;        -- 读写并发，崩溃恢复
PRAGMA busy_timeout=5000;       -- 写锁等待5秒
PRAGMA foreign_keys=ON;         -- 外键约束
PRAGMA cache_size=-20000;       -- 20MB内存缓存
PRAGMA temp_store=MEMORY;       -- 临时表存内存
PRAGMA synchronous=NORMAL;      -- 平衡性能和安全（WAL模式下足够）
PRAGMA auto_vacuum=INCREMENTAL; -- 增量回收空间
```

**定期维护**（应用启动时+每周一次）：
```sql
PRAGMA wal_checkpoint(TRUNCATE);  -- 检查点并截断WAL文件
PRAGMA optimize;                  -- 优化查询计划
-- 每月一次：
PRAGMA vacuum;                    -- 整理数据库文件（回收删除空间）
```

**评估员视角**：
- WAL文件可能增长到很大（长时间运行后），必须定期checkpoint
- `synchronous=NORMAL`在WAL模式下是安全的（不会损坏数据库），比FULL快很多
- 个人工具数据量小（<100MB），VACUUM很快，可每月执行

### 5.2 数据库连接管理

```python
# database.py
from sqlalchemy import create_engine, event
from sqlalchemy.orm import sessionmaker, Session

engine = create_engine(
    "sqlite:///data/app.db",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,  # 单连接（SQLite不支持连接池）
    echo=False,
)

SessionLocal = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)

@event.listens_for(engine, "connect")
def _set_pragma(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL")
    cursor.execute("PRAGMA busy_timeout=5000")
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.execute("PRAGMA cache_size=-20000")
    cursor.execute("PRAGMA temp_store=MEMORY")
    cursor.execute("PRAGMA synchronous=NORMAL")
    cursor.close()
```

**为什么用StaticPool**：SQLite的连接不是线程安全的，FastAPI异步框架下多线程访问同一连接会出问题。StaticPool确保所有请求共用一个连接，配合busy_timeout处理并发写入。

### 5.3 Repository模式

```python
# repositories/base.py
class BaseRepository(Generic[ModelType, CreateSchema, UpdateSchema]):
    model: type[ModelType]

    def __init__(self, db: Session):
        self.db = db

    def get(self, id: UUID) -> ModelType | None:
        return self.db.query(self.model).filter(self.model.id == id).first()

    def list(self, skip: int = 0, limit: int = 100, **filters) -> list[ModelType]:
        query = self.db.query(self.model)
        for key, value in filters.items():
            if value is not None:
                query = query.filter(getattr(self.model, key) == value)
        return query.offset(skip).limit(limit).all()

    def create(self, obj_in: CreateSchema) -> ModelType:
        obj = self.model(**obj_in.model_dump())
        self.db.add(obj)
        self.db.commit()
        self.db.refresh(obj)
        return obj

    def update(self, id: UUID, obj_in: UpdateSchema) -> ModelType:
        obj = self.get(id)
        if not obj:
            raise NotFoundException(f"{self.model.__name__} not found")
        update_data = obj_in.model_dump(exclude_unset=True)
        for field, value in update_data.items():
            setattr(obj, field, value)
        self.db.commit()
        self.db.refresh(obj)
        return obj

    def delete(self, id: UUID) -> None:
        obj = self.get(id)
        if not obj:
            raise NotFoundException(...)
        self.db.delete(obj)
        self.db.commit()
```

**评估员挑剔点**：
- 所有写操作必须在同一事务中，禁止部分提交
- 删除操作一期硬删除，但代码中预留`deleted_at`字段（二期软删除只需改query）
- 列表查询必须有分页，禁止`SELECT * FROM table`全表扫描

### 6.2 LLM客户端抽象

```python
# client.py
class LLMClient(ABC):
    @abstractmethod
    async def chat_completion(self, messages: list[dict], stream: bool = False, **kwargs):
        ...

    @abstractmethod
    async def chat_completion_stream(self, messages: list[dict], **kwargs) -> AsyncGenerator[str, None]:
        ...

class DeepSeekClient(LLMClient):
    """DeepSeek API实现（OpenAI兼容格式）"""
    def __init__(self, api_key: str, base_url: str = "https://api.deepseek.com/v1"):
        self.client = AsyncOpenAI(api_key=api_key, base_url=base_url)

    async def chat_completion_stream(self, messages, model="deepseek-chat", temperature=0.7, max_tokens=2000):
        stream = await self.client.chat.completions.create(
            model=model, messages=messages, stream=True,
            temperature=temperature, max_tokens=max_tokens,
        )
        async for chunk in stream:
            if chunk.choices[0].delta.content:
                yield chunk.choices[0].delta.content
```

**为什么抽象**：二期要支持本地模型（Ollama）和其他云端模型（通义），抽象层让切换零成本。一期只有DeepSeek实现，但接口已预留。

### 6.3 Prompt构建器（统一管理）

```python
# prompt_builder.py
class PromptBuilder:

    @staticmethod
    def system_persona() -> str:
        """第二分身的角色设定（一期调试阶段打磨）"""
        return """你是用户的第二分身，一个住在用户电脑里的AI伙伴。
```

### 6.4 对话服务（流式+历史管理）

```python
# chat_service.py
class ChatService:
    MAX_HISTORY_TURNS = 20  # 最多保留20轮
    MAX_CONTEXT_TOKENS = 6000  # 上下文Token上限

    async def send_message_stream(
        self, conversation_id: UUID, content: str, referenced_doc_ids: list[UUID] = None
    ) -> AsyncGenerator[str, None]:
        # 1. 保存用户消息
        self.message_repo.create(conversation_id, "user", content)

        # 2. 构建上下文
        messages = self._build_context(conversation_id, content, referenced_doc_ids)

        # 3. 流式调用
        full_response = ""
        async for chunk in self.llm.chat_completion_stream(messages):
            full_response += chunk
            yield chunk

        # 4. 保存助手消息（流式完成后）
        tokens = self.token_manager.count_tokens(messages + [{"role": "assistant", "content": full_response}])
        self.message_repo.create(conversation_id, "assistant", full_response, tokens=tokens)

    def _build_context(self, conversation_id, user_content, referenced_doc_ids):
        # 系统角色
        messages = [{"role": "system", "content": PromptBuilder.system_persona()}]

        # 引用文档注入
        if referenced_doc_ids:
            for doc_id in referenced_doc_ids:
                doc = self.document_repo.get(doc_id)
                if doc:
                    messages.append({"role": "system", "content": f"参考文档《{doc.title}》：\n{doc.content_text[:2000]}"})

        # 历史消息（最近N轮）
        history = self.message_repo.list_recent(conversation_id, limit=self.MAX_HISTORY_TURNS)
        messages.extend(history)

        # 当前用户消息
        messages.append({"role": "user", "content": user_content})

        # Token超限截断（保留系统消息+最近消息）
        return self.token_manager.truncate_messages(messages, self.MAX_CONTEXT_TOKENS)
```

**评估员挑剔点**：
- 流式响应中断时（网络断开），已生成的部分内容是否保存？→ 保存已生成部分，标记为`interrupted`
- 引用文档内容注入到system还是user？→ system（避免用户消息被污染）
- 历史消息截断策略：保留系统消息+引用文档+最近N轮，更早的生成摘要注入

### 6.5 异步AI任务（摘要/标签/灵感）

文档保存后触发的AI任务是异步的，不阻塞HTTP响应。

```python
# workers/ai_worker.py
class AIWorker:
    """后台AI任务处理器，订阅事件总线"""

    def __init__(self):
        event_bus.subscribe("document.saved", self._on_document_saved)

    async def _on_document_saved(self, document_id: UUID):
        try:
            doc = document_repo.get(document_id)
            if not doc or len(doc.content_text) < 50:
                return  # 内容太短不处理

            # 并行生成摘要和标签（用asyncio.gather）
            summary_task = summary_service.generate(doc)
            tags_task = tag_service.suggest(doc)
            summary, tags = await asyncio.gather(summary_task, tags_task)

            # 保存结果（不直接更新，而是存到ai_suggested字段，等用户确认）
            document_repo.update_ai_suggestions(document_id, summary, tags)

            # 60%概率触发灵感
            if random.random() < 0.6:
                inspiration = await inspiration_service.generate(doc)
                event_bus.publish("inspiration.generated", document_id=document_id, inspiration=inspiration)

        except Exception:
            logger.exception(f"AI处理失败: document_id={document_id}")
            # 静默失败，不影响主流程
```

**评估员视角**：
- 异步任务失败必须静默（不能弹窗打扰用户），但必须记录日志
- 摘要/标签结果先存`ai_suggested`字段，不直接覆盖用户数据（用户确认后才应用）
- 灵感生成是概率性的，路演版可设为100%确保演示效果

### 6.6 错误处理与降级

| 错误场景 | 处理方式 | 用户感知 |
|----------|----------|----------|
| API Key未配置 | 对话功能显示引导，摘要/标签不触发 | 提示"请先配置API Key" |
| 网络断开 | 对话发送失败+重试按钮；异步任务静默跳过 | 对话显示错误，其他功能正常 |
| API超时（30s） | 中断流式，已生成内容保存+标记 | 显示"响应中断，已保存部分内容" |
| API限流（429） | 等待5秒重试1次，仍失败则报错 | 显示"服务繁忙，请稍后重试" |
| API余额不足 | 捕获402错误，引导充值 | 显示"API余额不足" |
| 返回格式错误（标签非JSON） | 正则提取+容错解析，失败则返回空 | 标签建议可能为空，不报错 |

**降级策略**：AI功能全部不可用时，产品退化为纯工具（任务/文档/复盘正常），桌宠变为纯规则提醒器。

### 6.7 Token成本控制

1. **历史截断**：超过20轮或6000Token时，早期对话生成摘要后注入（二期）
2. **文档截断**：引用文档最多取前4000字，超长文档先AI生成摘要再注入
3. **模型分级**：摘要/标签用低参数模型（deepseek-chat），对话用标准模型
4. **缓存**：相同文档的摘要/标签结果缓存1小时（文档未修改时不重复生成）
5. **统计**：每次调用记录Token消耗，设置页展示累计消耗（二期）

```typescript
// pet-store.ts
type PetAction = 'idle' | 'thinking' | 'celebrating' | 'worried' | 'pointing' | 'working' | 'inspiration' | 'greeting';

interface PetState {
  currentAction: PetAction;
  actionTimer: number | null;
}

// 动作优先级（高优先级打断低优先级）
const ACTION_PRIORITY: Record<PetAction, number> = {
  inspiration: 8,
  celebrating: 7,
  worried: 6,
  pointing: 5,
  thinking: 4,
  working: 3,
  greeting: 2,
  idle: 1,
};

function triggerAction(action: PetAction, duration: number = 3000) {
  if (ACTION_PRIORITY[action] < ACTION_PRIORITY[state.currentAction]) {
    return; // 低优先级不打断高优先级
  }
  state.currentAction = action;
  if (state.actionTimer) clearTimeout(state.actionTimer);
  if (action !== 'idle') {
    state.actionTimer = setTimeout(() => {
      state.currentAction = 'idle';
    }, duration);
  }
}
```

## 第八章：状态机设计

### 8.1 任务状态机

```
           ┌──────────┐
           │  pending │◄──────────────┐
           └────┬─────┘               │
                │ 开始                 │ 恢复
                ▼                     │
           ┌──────────┐               │
     ┌────►│in_progress│──────┐       │
     │     └────┬─────┘      │       │
等待中│          │ 完成       │ 等待   │
     │          ▼            ▼       │
     │     ┌──────────┐ ┌─────────┐  │
     │     │completed │ │ waiting │──┘
     │     └──────────┘ └─────────┘
     │
     └── 等待中继续
```

**状态流转规则**：
| From | To | 触发 | 副作用 |
|------|----|------|--------|
| pending | in_progress | 用户点击"开始" | 记录开始时间 |
| pending | waiting | 用户标记"等待" | 无 |
| pending | completed | 用户直接完成 | 记录completed_at |
| in_progress | completed | 用户完成/提交成果 | 记录completed_at，触发桌宠庆祝，发布task.completed事件 |
| in_progress | waiting | 用户转等待 | 无 |
| waiting | in_progress | 继续进行 | 无 |
| waiting | pending | 重新规划 | 无 |
| completed | pending | 恢复未完成 | 清除completed_at |

**非法流转**（API层拒绝，返回3001错误）：
- completed → waiting（必须先恢复为pending）
- 任何状态 → 已删除（软删除，二期）

**实现**：在TaskService中封装状态流转方法，不允许直接update status字段：
```python
class TaskService:
    def start_task(self, task_id: UUID) -> Task:
        task = self.repo.get(task_id)
        if task.status not in ('pending', 'waiting'):
            raise TaskStateException(f"不能从{task.status}开始")
        return self.repo.update(task_id, TaskUpdate(status='in_progress'))

    def complete_task(self, task_id: UUID) -> Task:
        task = self.repo.get(task_id)
        if task.status == 'completed':
            return task  # 幂等
        if task.status not in ('pending', 'in_progress', 'waiting'):
            raise TaskStateException(...)
        result = self.repo.update(task_id, TaskUpdate(status='completed', completed_at=datetime.now()))
        event_bus.publish("task.completed", task_id=task_id)
        return result
```

### 8.2 文档生命周期

```
新建 → 编辑中 → 已保存 → 已修改 → 已保存 → ...
                ↓
            已删除（硬删除，二期软删除）
```

**文档状态**：
- `editing`：用户正在编辑（未保存）
- `saved`：已保存到数据库和文件
- `ai_pending`：AI处理中（摘要/标签生成中）

### 9.3 崩溃恢复

#### 9.3.1 Python子进程崩溃

```javascript
// main/backend-manager.js
class BackendManager {
  constructor() {
    this.restartCount = 0;
    this.maxRestarts = 3;
  }

  start() {
    this.process = spawn(pythonPath, ['-m', 'uvicorn', 'app.main:app', '--port', this.port]);
    this.process.on('exit', (code) => {
      if (code !== 0 && this.restartCount < this.maxRestarts) {

}
```

- 文档编辑器每30秒自动保存到数据库
- 同时维护`drafts/`目录，存储未保存的草稿（JSON格式）
- 应用崩溃重启后，检测到未保存草稿，提示"检测到未保存的内容，是否恢复？"
- 草稿保留7天，超过自动清理

### 9.4 数据一致性保证

**文档双写一致性**：
- 先写数据库（事务），成功后异步写Markdown文件
- 文件写入失败：记录到`pending_writes`表，后台重试（指数退避，最多5次）
- 定期校验：每周扫描数据库与文件，不一致时以数据库为准重建文件

**任务进度一致性**：
- 子任务完成时，在同一事务中更新父任务进度（避免部分更新）
- 进度计算用数据库触发器或service层原子操作，禁止前端计算后回传

**评估员视角挑剔点**：
- ❌ 禁止在渲染进程中`require('electron')`或任何Node模块
- ❌ 禁止`remote`模块（已废弃，安全风险）
- ❌ 禁止`webview`标签（安全风险）
- ✅ preload脚本是渲染进程访问原生API的唯一通道，且只暴露白名单方法
- ✅ 所有远程内容（AI返回的Markdown）渲染时必须做XSS过滤（DOMPurify）

### 10.2 API Key安全

**加密存储**：
```python
# core/security.py
import win32crypt
import base64

def encrypt_api_key(plaintext: str) -> str:
    """使用Windows DPAPI加密，密钥绑定当前用户账户"""
    encrypted = win32crypt.CryptProtectData(
        plaintext.encode('utf-8'),
        desc="Venustech API Key",
        flags=win32crypt.CRYPTPROTECT_LOCAL_MACHINE,
    )
    return base64.b64encode(encrypted).decode()

def decrypt_api_key(ciphertext: str) -> str:
    encrypted = base64.b64decode(ciphertext)
    _, decrypted = win32crypt.CryptUnprotectData(encrypted)
    return decrypted.decode('utf-8')
```

**安全规则**：
- API Key加密后存数据库，不明文存配置文件
- 解密仅在内存中进行，不写入日志
- API请求时从内存读取，用完即销毁（del变量）
- 设置页显示API Key时用`****`掩码，点击"显示"需二次确认
- 日志中脱敏（只显示前4位+后4位，如`sk-1234****abcd`）

### 10.3 XSS防护

- 所有用户输入的内容渲染时用DOMPurify过滤
- Tiptap编辑器默认开启XSS过滤
- AI返回的Markdown内容渲染前必须过滤（AI可能返回恶意脚本）
- 文档标题、标签等插入DOM时用Vue的文本插值（`{{ }}`），不用`v-html`
- 必须用`v-html`的地方（富文本渲染），先经过DOMPurify.sanitize()

### 10.4 依赖安全

- 定期运行`npm audit`和`pip-audit`检查依赖漏洞
- 锁定依赖版本（package-lock.json + requirements.txt）
- 不安装不必要的依赖（Electron应用包体和攻击面都要控制）
- CI/CD中加入依赖安全扫描步骤

### 10.5 本地数据安全

- 数据目录默认在`%APPDATA%`（用户目录，其他用户无权限）
- 一期不做全盘加密（二期可选加密仓库）
- 导出备份时不包含API Key（防止备份泄露导致Key被盗）
- 卸载应用时保留数据目录（防误删），提供"清除所有数据"选项

## 第十一章：性能优化

### 11.1 启动性能优化

**目标**：冷启动≤5秒（低端机），≤3秒（主流配置）

| 优化项 | 方案 | 预期收益 |
|--------|------|----------|
| 后端预加载 | 主进程启动时立即spawn Python，不等前端加载 | 节省1-2秒 |
| 前端懒加载 | 路由级代码分割，首屏只加载Dashboard | 首屏JS减少60% |
| Element Plus按需引入 | 只注册用到的组件，不用全量引入 | 包体减少40% |
| 后端依赖精简 | 只导入必要模块，延迟导入重型依赖 | Python启动加快 |
| 显示启动页 | 立即显示加载动画（不等后端就绪） | 感知启动时间减半 |
| SQLite预热 | 启动时执行一次简单查询，建立缓存 | 首次查询加快 |
| 桌宠延迟创建 | 主窗口渲染完成后再创建桌宠窗口 | 首屏加快 |

**启动时序优化**：
```
T0: 主进程启动
T0+50ms: spawn Python（并行）
T0+100ms: 创建主窗口+加载启动页
T0+200ms: 前端Vue启动（显示加载动画）
T0+1500ms: Python就绪（健康检查通过）
T0+1600ms: 前端请求数据
T0+2000ms: 首页渲染完成
T0+2500ms: 创建桌宠窗口
```

### 11.2 运行时性能

**数据库**：
- 所有查询走索引（用EXPLAIN QUERY PLAN验证）
- 列表查询分页（默认20条），禁止全表加载
- 首页聚合查询用单条SQL（JOIN），不用N+1查询
- 热点数据（今日任务、配置）内存缓存（TTL 30秒）

**前端渲染**：
- 长列表虚拟滚动（>100条启用）
- 大文档（>5000字）禁用实时预览，改为手动保存
- 对话消息虚拟滚动（>50条启用）
- 用`shallowRef`存储列表数据（避免深层响应式开销）
- 频繁更新的数据（流式文本）用`ref`+手动触发更新，不用`reactive`

**桌宠**：
- 动画用CSS transform/opacity（GPU加速），不用JS修改top/left
- 桌宠窗口最小化时暂停动画（`document.hidden`监听）
- 帧图片预加载，避免切换动作时闪烁
- 桌宠窗口不开启DevTools（生产环境）

**内存管理**：
- 离开页面时清理定时器/事件监听器（onUnmounted）
- 对话历史分页加载（默认最近50条，向上滚动加载更多）
- 图片懒加载（IntersectionObserver）
- 定期清理Blob URL（文档图片预览）
- Electron：限制渲染进程内存（`app.commandLine.appendSwitch('js-flags', '--max-old-space-size=512')`）

### 11.3 性能监控

- 后端：每个API记录响应时间（中间件），超过1秒的记录warning日志
- 前端：关键操作打点（页面加载、API请求、编辑器保存），开发环境显示性能面板
- 应用启动时记录各阶段耗时，写入日志
- 定期检查内存占用，超过800MB时提示用户重启

## 第十七章：渲染性能深度优化（防卡顿专项）

> 本章是第十一章的深度扩展，聚焦"用户感知到的卡顿"。
> 核心指标：交互响应 ≤100ms，动画稳定60fps，长任务 ≤50ms，输入延迟 ≤50ms。
> 参考模型：Google RAIL（Response/Animation/Idle/Load）。

### 17.1 卡顿根因分析

Electron渲染进程本质是Chromium，卡顿的四大根因：

| 根因 | 表现 | 典型场景 |
|------|------|----------|
| **主线程长任务** | 点击无响应、输入延迟 | 大列表渲染、JSON深拷贝、同步计算 |
| **频繁重排重绘** | 滚动掉帧、动画抖动 | 直接修改layout属性、未优化的动画 |
| **内存泄漏** | 越用越卡、最终崩溃 | 未清理的定时器/监听器、闭包持有DOM |
| **GPU层过多** | 内存暴涨、闪烁 | 滥用will-change、过多独立合成层 |

**诊断工具**：
- 开发环境：Chrome DevTools Performance面板（录制交互，看Long Task红色标记）
- 生产环境：`PerformanceObserver`埋点，长任务>50ms上报日志
- 内存：DevTools Memory面板，对比操作前后heap快照

### 17.2 长任务拆分策略

**原则**：任何同步代码块执行超过50ms，必须拆分。

#### 17.2.1 主线程调度优先级

```typescript
// utils/scheduler.ts
// 模拟浏览器scheduler API（Electron 28已支持scheduler.postTask，但做兼容封装）

type TaskPriority = 'user-blocking' | 'user-visible' | 'background';

export function scheduleTask<T>(fn: () => T, priority: TaskPriority = 'user-visible'): Promise<T> {
  return new Promise((resolve) => {
    if ('scheduler' in window && 'postTask' in (window as any).scheduler) {
      (window as any).scheduler.postTask(fn, { priority }).then(resolve);
    } else {
      // 降级：用setTimeout模拟优先级
      const delay = priority === 'user-blocking' ? 0 : priority === 'user-visible' ? 100 : 500;
      setTimeout(() => resolve(fn()), delay);
    }
  });
}

// 空闲时执行（不影响交互）
export function runWhenIdle(fn: () => void, timeout = 3000) {
  if ('requestIdleCallback' in window) {
    (window as any).requestIdleCallback(fn, { timeout });
  } else {
    setTimeout(fn, 200);
  }
}
```

**优先级分配**：
| 优先级 | 场景 | 延迟目标 |
|--------|------|----------|
| user-blocking | 点击反馈、路由切换、弹窗 | ≤16ms |
| user-visible | 列表渲染、数据格式化、AI流式文本更新 | ≤100ms |
| background | 日志上报、预加载、索引构建、缓存清理 | 空闲时 |

#### 17.2.2 Web Worker 计算卸载

以下操作必须放入Web Worker，禁止在主线程执行：

| 操作 | 原因 | Worker方案 |
|------|------|-----------|
| 大JSON序列化/反序列化 | 文档内容可能>100KB，同步parse阻塞 | Worker中parse后postMessage |
| Markdown↔JSON转换 | Tiptap JSON转Markdown是CPU密集 | Worker中调用转换库 |
| 全文搜索索引构建 | 倒排索引构建O(n)，文档多时卡顿 | Worker中构建，主线程查询 |
| 图片压缩/缩略图 | Canvas操作阻塞主线程 | OffscreenCanvas + Worker |
| 数据统计聚合 | 首页多维度统计计算 | Worker中聚合，返回结果 |

```typescript
// workers/document.worker.ts
/// <reference lib="webworker" />
import { JSONContent } from '@tiptap/core';
import { generateMarkdown, parseMarkdown } from '@/utils/markdown';

self.onmessage = (e: MessageEvent) => {
  const { type, payload } = e.data;
  switch (type) {
    case 'toMarkdown':
      self.postMessage({ type: 'result', result: generateMarkdown(payload as JSONContent) });
      break;
    case 'fromMarkdown':
      self.postMessage({ type: 'result', result: parseMarkdown(payload as string) });
      break;
  }
};
```

**评估员挑剔点**：
- Worker通信本身有开销（结构化克隆），小数据（<10KB）不值得放Worker
- Worker中不能访问DOM，所有DOM操作必须回主线程
- Worker数量控制：最多2个（文档转换+搜索索引），过多反而增加内存和调度开销
- 用Comlink库简化Worker通信（自动代理Promise），避免手写postMessage样板

#### 17.2.3 增量渲染（时间切片）

大列表/大文档不能一次性渲染，用时间切片分批：

```typescript
// composables/useIncrementalRender.ts
export function useIncrementalRender<T>(items: Ref<T[]>, batchSize = 20) {
  const visible = ref<T[]>([]);
  let index = 0;
  let rafId: number;

  function renderNextBatch() {
    const end = Math.min(index + batchSize, items.value.length);
    visible.value.push(...items.value.slice(index, end));
    index = end;
    if (index < items.value.length) {
      rafId = requestAnimationFrame(renderNextBatch);
    }
  }

  watch(items, () => {
    index = 0;
    visible.value = [];
    cancelAnimationFrame(rafId);
    rafId = requestAnimationFrame(renderNextBatch);
  }, { immediate: true });

  onUnmounted(() => cancelAnimationFrame(rafId));
  return { visible };
}
```

### 17.3 虚拟滚动深度方案

#### 17.3.1 何时启用虚拟滚动

| 列表类型 | 阈值 | 方案 |
|----------|------|------|
| 任务列表 | >100条 | 固定高度虚拟滚动 |
| 文档列表 | >100条 | 固定高度虚拟滚动 |
| 对话消息 | >50条 | 动态高度虚拟滚动（消息长度不一） |
| 复盘列表 | >50条 | 固定高度虚拟滚动 |

#### 17.3.2 动态高度虚拟滚动（对话场景）

对话消息高度不固定（短消息一行，长消息多行），标准虚拟滚动不适用。

**方案**：预估高度+实际测量修正
```typescript
// 虚拟滚动核心逻辑
interface VirtualItem {
  index: number;
  height: number;       // 预估高度
  measured: boolean;    // 是否已实际测量
  top: number;          // 累计偏移
}

class DynamicVirtualScroller {
  private items: VirtualItem[] = [];
  private estimatedHeight = 80; // 预估每条消息高度
  private overscan = 5;         // 上下额外渲染条数

  // 滚动时计算可见范围
  getVisibleRange(scrollTop: number, viewportHeight: number) {
    let start = 0;
    let accumulated = 0;
    // 二分查找起始索引（O(log n)）
    for (let i = 0; i < this.items.length; i++) {
      if (accumulated + this.items[i].height > scrollTop) { start = i; break; }
      accumulated += this.items[i].height;
    }
    const end = Math.min(this.items.length, start + Math.ceil(viewportHeight / this.estimatedHeight) + this.overscan);
    return { start: Math.max(0, start - this.overscan), end };
  }

  // 渲染后测量实际高度，修正后续偏移
  measureItem(index: number, actualHeight: number) {
    const item = this.items[index];
    if (!item.measured || item.height !== actualHeight) {
      const diff = actualHeight - item.height;
      item.height = actualHeight;
      item.measured = true;
      // 修正后续所有item的top偏移
      for (let i = index + 1; i < this.items.length; i++) {
        this.items[i].top += diff;
      }
    }
  }
}
```

**评估员视角**：
- 动态高度虚拟滚动的滚动条高度会随测量修正而跳动，需用平滑过渡或固定总高度（预估×总数）
- 对话场景消息通常不会超过500条，即使全量渲染也可接受，虚拟滚动是预防性优化
- 优先用成熟库`vue-virtual-scroller`（支持动态高度），不自己造轮子

#### 17.3.3 虚拟滚动的坑

| 坑 | 现象 | 解决方案 |
|----|------|----------|
| 快速滚动白屏 | 滚动速度超过渲染速度 | 增加overscan（上下多渲染5条） |
| 滚动位置错乱 | 动态加载更多后偏移未更新 | 加载更多后重新计算所有item的top |
| 输入框失焦 | 虚拟滚动回收了包含输入框的DOM | 正在编辑的消息固定不回收 |
| 滚动条不准 | 预估高度与实际差距大 | 测量后修正，或用ResizeObserver持续监听 |

#### 17.4.2 自动保存防抖与节流

```typescript
// composables/useAutoSave.ts
export function useAutoSave(editor: Ref<Editor | null>, documentId: string) {
  let saveTimer: number;
  let pending = false;

  // 输入后30秒保存（防抖）
  const debouncedSave = useDebounceFn(() => {
    if (!editor.value) return;
    pending = true;
    documentStore.saveDocument(documentId, editor.value.getJSON())
      .finally(() => { pending = false; });
  }, 30000);

  // 失焦立即保存
  const saveOnBlur = () => {
    if (pending) return;
    debouncedSave.cancel();
    documentStore.saveDocument(documentId, editor.value?.getJSON());
  };

  // 路由离开前强制保存
  onBeforeRouteLeave(() => {
    if (pending || editor.value) {
      // 同步保存（阻塞路由切换）
      return documentStore.saveDocument(documentId, editor.value?.getJSON());
    }
  });

  watch(() => editor.value?.state, debouncedSave);
  return { saveOnBlur };
}
```

**评估员挑剔点**：
- 自动保存不能太频繁（每次输入都保存→数据库写入+Markdown文件写入→卡顿）
- 30秒防抖是平衡点：最多丢30秒数据（可接受），写入频率合理
- 失焦保存+路由离开保存是兜底，确保不丢数据
- 保存时显示"已保存"指示器（右下角小字），给用户确定性

#### 17.4.3 大文档降级策略

| 文档字数 | 策略 |
|----------|------|
| <5000 | 完整功能（实时字数统计、双向链接高亮、AI建议） |
| 5000-20000 | 关闭实时字数统计（改为手动/失焦计算），关闭AI实时建议 |
| >20000 | 警告用户，建议拆分文档；编辑器关闭语法高亮扩展 |

### 17.5 流式渲染优化（AI对话）

AI流式响应是高频交互场景，每收到一个token就更新DOM会导致严重卡顿。

#### 17.5.1 批量DOM更新

```typescript
// composables/useStreamingText.ts
export function useStreamingText() {
  const text = ref('');
  let buffer = '';
  let rafId: number | null = null;

  function appendChunk(chunk: string) {
    buffer += chunk;
    if (rafId === null) {
      // 用requestAnimationFrame批量更新，一帧最多更新一次DOM
      rafId = requestAnimationFrame(() => {
        text.value += buffer;
        buffer = '';
        rafId = null;
      });
    }
  }

  function finish() {
    if (rafId !== null) {
      cancelAnimationFrame(rafId);
      text.value += buffer;
      buffer = '';
      rafId = null;
    }
  }

  onUnmounted(() => { if (rafId !== null) cancelAnimationFrame(rafId); });
  return { text, appendChunk, finish };
}
```

**为什么用rAF批量**：
- 网络可能每10ms就来一个token，一帧（16.6ms）内可能收到多个token
- 每次更新DOM触发重排，10ms一次=100次/秒，远超60fps
- rAF确保每帧只更新一次DOM，合并buffer中的所有token
- 视觉上无差异（人眼无法区分10ms和16ms的更新延迟）

#### 17.5.2 自动滚动优化

流式输出时自动滚动到底部，但用户手动向上滚动时不应强制滚回。

```typescript
const scrollContainer = ref<HTMLElement>();
const userScrolledUp = ref(false);

function handleScroll() {
  const el = scrollContainer.value;
  if (!el) return;
  // 距离底部>100px认为用户在看历史
  userScrolledUp.value = el.scrollHeight - el.scrollTop - el.clientHeight > 100;
}

function autoScroll() {
  if (userScrolledUp.value) return; // 用户在看历史，不打扰
  const el = scrollContainer.value;
  if (el) el.scrollTop = el.scrollHeight;
}

// 流式更新后调用
watch(text, () => nextTick(autoScroll));
```

#### 17.5.3 流式Markdown渲染

AI返回的是Markdown，不能等全部接收完再渲染（延迟高），也不能每个token都重新渲染完整Markdown（卡顿）。

**方案**：增量渲染+防抖
- 维护已渲染的Markdown文本和未渲染的增量
- 每500ms或每收到20个token，重新渲染一次完整Markdown
- 用`marked`+DOMPurify，渲染结果缓存

```typescript
const renderedHtml = ref('');
let renderTimer: number;

watch(text, () => {
  clearTimeout(renderTimer);
  renderTimer = window.setTimeout(() => {
    renderedHtml.value = DOMPurify.sanitize(marked.parse(text.value));
  }, 300);
});
```

### 17.6 CSS重排重绘控制

#### 17.6.1 动画只动transform和opacity

| 属性 | 触发 | 允许用于动画 |
|------|------|-------------|
| transform | 合成（GPU） | ✅ 推荐 |
| opacity | 合成（GPU） | ✅ 推荐 |
| top/left/width/height | 布局(Layout)+绘制(Paint) | ❌ 禁止 |
| margin/padding/border | 布局 | ❌ 禁止 |
| box-shadow/background | 绘制 | ⚠️ 尽量避免 |

```css
/* ❌ 错误：触发重排 */
.modal { transition: top 0.3s ease; }
.modal.show { top: 0; }

/* ✅ 正确：只触发合成 */
.modal { transform: translateY(100%); transition: transform 0.3s ease; }
.modal.show { transform: translateY(0); }
```

#### 17.6.2 contain属性隔离重排

```css
/* 任务卡片：内部变化不影响外部布局 */
.task-card {
  contain: layout paint style;
}

/* 虚拟滚动容器：内容变化不触发外部重算 */
.virtual-list {
  contain: strict; /* layout + paint + size + style */
}
```

#### 17.6.3 will-change慎用

```css
/* ❌ 错误：全局滥用，每个元素都提升为合成层，内存爆炸 */
* { will-change: transform; }

/* ✅ 正确：只在即将动画的元素上临时设置 */
.task-card:hover { will-change: transform; }
.task-card { transition: transform 0.2s; }
.task-card:active { transform: scale(0.98); }
```

**评估员视角**：每个`will-change`元素会创建独立合成层，占用GPU内存。超过10个合成层就可能导致内存问题。桌宠窗口本身是一个独立BrowserWindow（独立合成器），不受主窗口合成层数量影响。

### 17.7 内存泄漏防治

#### 17.7.1 常见泄漏模式与修复

| 泄漏模式 | 代码示例 | 修复 |
|----------|----------|------|
| 未清理定时器 | `setInterval`在组件内 | `onUnmounted(() => clearInterval(id))` |
| 未移除事件监听 | `window.addEventListener` | `onUnmounted(() => window.removeEventListener(...))` |
| 闭包持有DOM | 事件回调引用已卸载元素 | 用`WeakRef`或确保回调可被GC |
| Pinia store无限增长 | 对话历史全部存在内存 | 分页加载，只存当前对话 |
| 观察者未断开 | `ResizeObserver`/`IntersectionObserver` | `observer.disconnect()` in onUnmounted |
| 全局事件总线 | `eventBus.on`未`off` | 组件内订阅，卸载时取消订阅 |

#### 17.7.2 统一清理模式

```typescript
// composables/useCleanup.ts
// 提供统一的清理注册机制，避免遗漏
export function useCleanup() {
  const cleanups: (() => void)[] = [];

  function onCleanup(fn: () => void) {
    cleanups.push(fn);
  }

  onUnmounted(() => {
    cleanups.forEach(fn => {
      try { fn(); } catch (e) { console.error('清理失败', e); }
    });
    cleanups.length = 0;
  });

  return { onCleanup };
}

// 使用
const { onCleanup } = useCleanup();
const timer = setInterval(...);
onCleanup(() => clearInterval(timer));
```

### 17.9 启动性能进阶

#### 17.9.1 渐进式启动

```
T0: 应用启动
T0+50ms: 显示启动页（纯HTML/CSS，不依赖Vue）
T0+100ms: Vue应用开始加载（同时Python后端启动）
T0+300ms: Vue挂载完成，显示骨架屏
T0+1500ms: 后端就绪，请求数据
T0+1800ms: 数据返回，骨架屏→真实内容
T0+2500ms: 桌宠窗口创建
```

**关键**：启动页用Electron的`show:false`+`ready-to-show`事件，避免白屏闪烁。

#### 17.9.2 预加载策略

- 路由懒加载：非首页路由动态import
- 组件懒加载：大组件（编辑器、看板）用`defineAsyncComponent`
- 数据预取：首页数据在后端启动时就开始查询（不等前端请求）
- 图片预加载：桌宠帧图片在空闲时预加载

#### 17.9.3 后端启动优化

- Python延迟导入：重型库（openai、sqlalchemy）在用到时才import，不在模块顶层
- Uvicorn用`--workers 1`（单进程足够，避免多进程SQLite锁冲突）
- 数据库连接在启动时预热（执行一次`SELECT 1`）
- Alembic迁移在启动时同步执行（确保schema最新），但加超时（10秒）

### 17.10 感知性能优化

感知性能 ≠ 实际性能，用户"觉得快"比"实际快"更重要。

| 技术 | 场景 | 效果 |
|------|------|------|
| 乐观更新 | 创建/完成任务：先更新UI，后台同步 | 操作即时反馈，失败时回滚 |
| 骨架屏 | 页面加载、列表加载 | 比loading转圈更有"内容即将出现"的感知 |
| 过渡动画 | 路由切换、弹窗、侧边栏 | 掩盖加载时间，视觉流畅 |
| 即时视觉反馈 | 按钮点击:active状态、hover | 100ms内有反馈，用户觉得"响应了" |
| 进度指示 | AI生成、备份导出 | 不确定等待→确定等待，焦虑降低 |
| 占位内容 | 空列表显示引导插图+操作按钮 | 空白页→有内容的页面，感知更完整 |

**乐观更新示例**：
```typescript
async function toggleTask(task: Task) {
  const originalStatus = task.status;
  // 1. 立即更新UI（乐观）
  task.status = originalStatus === 'completed' ? 'pending' : 'completed';
  try {
    await taskStore.updateTask(task.id, { status: task.status });
  } catch (e) {
    // 2. 失败回滚
    task.status = originalStatus;
    toast.error('操作失败，已恢复');
  }
}
```

### 17.11 性能监控与告警

```typescript
// core/performance-monitor.ts
if (import.meta.env.DEV) {
  // 长任务监控
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      if (entry.duration > 50) {
        console.warn(`[长任务] ${entry.duration.toFixed(0)}ms`, entry);
      }
    }
  });
  observer.observe({ type: 'longtask', buffered: true });

  // 帧率监控
  let frames = 0;
  let lastTime = performance.now();
  function measureFPS() {
    frames++;
    const now = performance.now();
    if (now - lastTime >= 1000) {
      const fps = Math.round(frames * 1000 / (now - lastTime));
      if (fps < 50) console.warn(`[帧率] ${fps}fps（低于50）`);
      frames = 0;
      lastTime = now;
    }
    requestAnimationFrame(measureFPS);
  }
  requestAnimationFrame(measureFPS);
}
```

| 首屏渲染时间 | <2秒 | 开发环境Performance面板验证 |
| 交互响应 | <100ms | 长任务监控 |
| 动画帧率 | ≥55fps | 帧率监控 |
| 内存占用 | <500MB（空闲） | 内存监控 |
| 包体 | <200MB（安装包） | 构建脚本检查 |

#### 18.2.1 API类型自动生成


## 第十九章：体验优良性设计

> 本章从用户感知角度定义体验标准，不只是"能用"，而是"好用、想用、离不开"。
> 核心法则：**即时反馈、可恢复、可预测、可掌控**。

### 19.1 响应式交互（100ms法则）

| 操作类型 | 响应时间目标 | 实现方式 |
|----------|-------------|----------|
| 按钮点击/开关切换 | ≤50ms | 纯前端状态变更，不等待API |
| 路由切换 | ≤100ms | 骨架屏+过渡动画，掩盖加载 |
| 列表筛选/排序 | ≤100ms | 前端本地筛选（数据已加载） |
| 保存操作 | ≤300ms | 乐观更新+后台同步 |
| API请求 | ≤1秒 | 超时30秒，loading指示器 |
| AI生成 | 首字≤2秒 | 流式输出，进度指示 |

**即时反馈实现**：
```typescript
// 所有按钮点击都有视觉反馈
.button {
  transition: transform 0.1s, background-color 0.15s;
}
.button:active {
  transform: scale(0.96);  // 按下反馈
}
.button:disabled {
  opacity: 0.5; cursor: not-allowed;
}
```

### 19.2 状态可见性（三态设计）

每个数据展示区域必须设计三种状态：

| 状态 | 设计 | 示例 |
|------|------|------|
| 加载中 | 骨架屏（内容形状占位） | 任务列表骨架屏 |
| 空状态 | 插图+引导文案+操作按钮 | "还没有任务，点击创建第一个" |
| 错误 | 错误图标+原因+重试按钮 | "加载失败，请检查网络 [重试]" |

**空状态设计原则**：
- 不只是"暂无数据"四个字
- 告诉用户为什么空（是还没创建？还是筛选条件太严？）
- 给出下一步操作（创建按钮/清除筛选）

### 19.3 错误恢复体验

#### 19.3.1 撤销机制

危险操作支持撤销（5秒窗口）：
```typescript
// 删除任务后显示Toast："已删除 [撤销]"
async function deleteTask(task: Task) {
  const snapshot = { ...task };
  await taskStore.deleteTask(task.id);
  const toast = toast.warning('已删除任务', {
    action: { label: '撤销', onClick: () => taskStore.restoreTask(snapshot) },
    duration: 5000,
  });
}
```

一期硬删除，但UI层实现"软撤销"（删除后5秒内可恢复，5秒后真正删除）。

#### 19.3.2 自动保存与恢复

- 文档每30秒自动保存
- 应用崩溃重启后检测未保存草稿，提示恢复
- 编辑器内容在输入时同步存到localStorage（兜底）

#### 19.3.3 操作确认分级

| 操作风险 | 确认方式 |
|----------|----------|
| 低（标记完成、编辑） | 无需确认，支持撤销 |
| 中（删除任务、删除文档） | Toast撤销（5秒） |
| 高（清空数据、删除文件夹、覆盖备份） | Modal二次确认+输入确认文字 |
