### 1.2 核心业务域划分（DDD 限界上下文）

| 限界上下文 | 核心职责 | 包含聚合根 |
|------------|----------|-----------|
| **身份与访问** | 用户注册登录、权限、个人设置 | User, Setting |
| **任务域** | 今日聚焦、待办、任务状态流转 | Task, FocusTask |
| **项目域** | 多项目管理、进度追踪、阶段管理 | Project, Milestone |
| **知识域** | 收集箱、知识库、文档、标签、资源分类 | Knowledge, Document, Tag |
| **学习域** | 学习计划、知识卡片、间隔重复复习 | StudyPlan, FlashCard |
| **生活域** | 生活记录、精力追踪、四维日记 | LifeLog, Energy |
| **AI协作域** | 对话、Prompt模板、AI任务拆解、项目记忆 | Conversation, Prompt, AITask |
| **资产域** | SOP流程、Skill技能、项目记忆复用 | SOP, Skill, ProjectMemory |

**域间关系**：以「任务」为核心枢纽，任务关联项目、关联知识文档、关联 AI 对话；资产域为所有域提供可复用能力。

### 1.3 架构决策：单体而非微服务

选择**模块化单体（Modular Monolith）**：

- 独立开发者，微服务运维成本、分布式事务、服务通信复杂度远超收益
- 各业务域通过 Python 包隔离，接口清晰，未来如需拆分可平滑迁移
- 单机部署，Docker Compose 一键启动，开发调试效率高
- 个人工具类产品并发极低（单用户或小团队），单体性能够用

### 2.4 部署方案

```yaml
# docker-compose.yml 核心服务
services:
  frontend:       # Nginx 托管构建后的静态文件 + 反向代理
  backend:        # FastAPI + Uvicorn/Gunicorn
  postgres:       # 数据库
  redis:          # 缓存
  # celery_worker: # MVP 后加入，处理异步任务
```

- **反向代理**：Nginx 统一入口，`/api` 转发 FastAPI，`/` 指向前端静态文件

### 3.2 核心表结构

**users（用户表）**

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) UNIQUE NOT NULL,
    username VARCHAR(50) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    avatar_url VARCHAR(500),
    settings JSONB DEFAULT '{}',  -- 个人设置（主题、通知偏好等）
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**projects（项目表）**

```sql
CREATE TABLE projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    name VARCHAR(200) NOT NULL,
    description TEXT,
    status VARCHAR(20) DEFAULT 'active',  -- active/paused/completed/archived
    progress INTEGER DEFAULT 0,  -- 0-100 冗余字段，定时计算
    color VARCHAR(20),  -- 项目标识色
    sort_order INTEGER DEFAULT 0,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_projects_user_id ON projects(user_id);
```

**tasks（任务表）**

```sql
CREATE TABLE tasks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    project_id UUID REFERENCES projects(id) ON DELETE SET NULL,
    title VARCHAR(500) NOT NULL,
    description TEXT,
    status VARCHAR(20) DEFAULT 'pending',  -- pending/in_progress/waiting/completed
    priority VARCHAR(20) DEFAULT 'medium', -- low/medium/high/urgent
    is_focus BOOLEAN DEFAULT FALSE,  -- 是否为今日最重要
    due_date DATE,
    completed_at TIMESTAMPTZ,
    sort_order INTEGER DEFAULT 0,
    metadata JSONB DEFAULT '{}',  -- 灵活扩展：AI 拆解结果、来源等
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_tasks_user_status ON tasks(user_id, status);
CREATE INDEX idx_tasks_focus ON tasks(user_id, is_focus) WHERE is_focus = TRUE;
```

**documents（文档/笔记表）**

```sql
CREATE TABLE documents (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    project_id UUID REFERENCES projects(id) ON DELETE SET NULL,
    title VARCHAR(500) NOT NULL,
    content JSONB,  -- Tiptap 富文本 JSON 结构
    category VARCHAR(30) DEFAULT 'inbox',  -- inbox/knowledge/project/study
    version INTEGER DEFAULT 1,
    tags TEXT[] DEFAULT '{}',  -- PostgreSQL 数组，简化标签查询
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_documents_user_category ON documents(user_id, category);
CREATE INDEX idx_documents_tags ON documents USING GIN(tags);
```

**conversations（AI 对话表）**

```sql
CREATE TABLE conversations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(200),
    scene VARCHAR(30) DEFAULT 'general',  -- general/brainstorm/task_break/writing/qa
    related_task_id UUID REFERENCES tasks(id) ON DELETE SET NULL,
    related_project_id UUID REFERENCES projects(id) ON DELETE SET NULL,
    model VARCHAR(50) DEFAULT 'deepseek-chat',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**messages（对话消息表）**

```sql
CREATE TABLE messages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID REFERENCES conversations(id) ON DELETE CASCADE,
    role VARCHAR(20) NOT NULL,  -- user/assistant/system
    content TEXT NOT NULL,
    tokens INTEGER,  -- 消耗 token 数，用于成本统计
    created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_messages_conversation ON messages(conversation_id, created_at);
```

**prompts（Prompt 模板表）**

```sql
CREATE TABLE prompts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    title VARCHAR(200) NOT NULL,
    content TEXT NOT NULL,  -- 模板内容，支持 {{变量}} 占位
    category VARCHAR(50),  -- 写作/分析/编程等
    variables JSONB DEFAULT '[]',  -- 变量定义列表
    usage_count INTEGER DEFAULT 0,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

`study_plans / flash_cards / life_logs / sops / skills / project_memories` 等表结构类似，遵循统一模式：`id + user_id + 业务字段 + metadata JSONB + 时间戳`。

### 3.3 设计要点

1. **统一主键**：全部 UUID，避免 ID 枚举攻击，分布式友好
2. **软删除**：所有业务表增加 `deleted_at TIMESTAMPTZ NULL`，查询默认过滤，MVP 阶段可先不加，后续按需
3. **JSONB 灵活字段**：`metadata`、`settings`、`content` 用 JSONB，应对需求变化，避免频繁加列
4. **标签用数组**：PostgreSQL `TEXT[]` + GIN 索引，比中间表查询简单，适合个人工具标签规模
5. **进度冗余**：项目进度用冗余字段存储，任务完成事件触发更新，避免每次查询实时计算

## 4. API 设计

### 4.1 统一规范

- **基础路径**：`/api/v1`
- **认证**：Header `Authorization: Bearer <JWT>`
- **统一响应格式**：

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "timestamp": 1710000000
}
```

- **分页**：`?page=1&page_size=20`，响应含 `total`、`page`、`page_size`、`list`
- **错误码**：`0` 成功，`1xxx` 参数错误，`2xxx` 认证错误，`3xxx` 业务错误，`5xxx` 服务器错误

### 4.3 AI 流式响应（SSE）

```python
# FastAPI SSE 示例
from fastapi.responses import StreamingResponse

@router.post("/conversations/{id}/messages")
async def send_message(conversation_id: UUID, request: MessageRequest):
    async def event_generator():
        async for chunk in llm_client.stream_chat(messages):
            yield f"data: {chunk.content}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

前端用 `EventSource` 或 `fetch + ReadableStream` 接收流式数据，逐字渲染。

| Store | 职责 | 持久化 |
|-------|------|--------|
| `userStore` | 用户信息、token、登录状态 | 是（localStorage） |
| `appStore` | 侧边栏折叠/展开、主题色、全局 loading | 是 |
| `taskStore` | 今日任务列表、聚焦任务、任务筛选条件 | 否 |
| `aiStore` | 当前对话、消息列表、流式状态 | 否 |

### 5.5 AI 对话前端方案

- 对话窗口用**右侧抽屉（Drawer）**形式，不离开当前页面
- 流式接收用 `fetch + ReadableStream`（比 EventSource 更灵活，支持 POST body）
- 消息列表虚拟滚动（对话量大时性能优化）
- 快捷标签（头脑风暴/任务拆解/写作助手/知识问答）点击后自动填入预设 Prompt 并发送

## 6. AI 能力层设计

### 6.1 架构定位

AI 作为**应用内独立模块**，不单独部署服务。通过 `app/services/ai/` 包统一封装，对外提供高层接口，底层可切换不同 LLM 提供商。

```
backend/app/services/ai/
├── __init__.py
├── client.py          # LLM 客户端抽象（兼容 OpenAI 格式）
├── chat.py            # 对话服务
├── templates.py       # Prompt 模板渲染（Jinja2 风格变量替换）
├── task_breaker.py    # 任务拆解专用服务
├── writing_assistant.py # 写作助手
└── memory.py          # 项目记忆检索
```

### 6.2 方案对比：Prompt 管理

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| **A. 数据库存储 Prompt 模板** | 用户可自定义、可统计使用次数、支持版本 | 需要 CRUD 界面 | ✅ MVP 采用 |
| B. 代码中硬编码 Prompt | 开发快、无需界面 | 用户不可修改、迭代需发版 | 仅用于系统级 Prompt |
| C. 配置文件 YAML/JSON | 结构化、可版本控制 | 用户不可动态修改 | 不推荐 |

**推荐方案 A**：系统内置一批高质量 Prompt 模板（种子数据），用户可复制修改为自己的模板，存储在 `prompts` 表。

### 6.3 方案对比：项目记忆实现

| 方案 | 原理 | 优点 | 缺点 | 推荐阶段 |
|------|------|------|------|----------|
| **A. 关键词检索 + 上下文拼接** | 项目相关文档/对话摘要通过关键词匹配，拼接到 Prompt | 实现简单、无额外依赖 | 召回精度低、上下文长度受限 | MVP |
| B. 向量数据库 RAG | 文档向量化存入 Chroma/Qdrant，语义检索 | 召回精度高、支持大规模知识 | 增加运维复杂度、需要 Embedding API | V2 迭代 |
| C. 结构化项目摘要 | AI 定期生成项目状态摘要，对话时注入 | 信息密度高、Token 省 | 需要定时任务、摘要可能遗漏细节 | V2 迭代 |

**MVP 采用方案 A**：创建对话时若关联了项目，自动从该项目文档标题 + 最近对话中提取关键词匹配，取 Top3 文档摘要拼入 system prompt。后续 V2 引入向量数据库升级 RAG。

### 6.4 Token 成本控制

1. **对话历史截断**：每次请求只携带最近 N 轮对话（如 10 轮），更早历史生成摘要后注入
2. **流式响应不存储中间态**：只在完成后存储完整 assistant 消息
3. **模型分级**：简单任务（如格式化）用便宜模型，复杂任务（如任务拆解）用强模型
4. **缓存**：相同 Prompt + 相同输入结果缓存到 Redis（TTL 1 小时），避免重复调用

## 7. 架构设计哲学

> **"模块化单体 + JSONB 灵活字段 + AI 可插拔"**

- 模块化单体：单人也能维护，未来可拆分
- JSONB + 数组：数据模型应对需求变化，减少迁移痛苦
- AI 层抽象：自由切换 LLM 提供商，不被绑定
- MVP 聚焦核心闭环：2 周看到可用产品，避免完美主义
