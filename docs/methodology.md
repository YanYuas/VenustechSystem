# Venustech System 方法论说明书

> 本项目遵循的工程思维与配置管理方法论。
> 来源：《工程思维与配置管理思维——从项目目录结构看软件工程的底层方法论》
> 全局范式见 `~/.claude/reference/project-init-spec.md`

## 一、核心认知

**目录结构是思维的外化，不是收纳术。** 每个目录名对应一种工程决策。工具会迭代，思维需沉淀。

三流工程师写代码，二流工程师建系统，一流工程师定规则。

## 二、本项目目录结构

```
Venustech System/
├── src/              # 源码
├── tests/            # 测试
├── docs/             # 文档
│   ├── design/       #   设计文档（架构/接口/DB/UI）
│   ├── management/   #   管理文档（计划/纪要/决策日志）
│   └── methodology.md #  本方法论
├── scripts/          # 脚本
├── config/           # 配置
├── README.md         # 项目说明
├── CHANGELOG.md      # 变更日志（Keep a Changelog）
└── CONTRIBUTING.md   # 贡献指南
```

## 三、版本控制规范

| 分支 | 用途 | 规则 |
|------|------|------|
| `main` | 稳定主线，始终可构建可交付 | **受保护**，禁止直接 push，必须 PR 合并 |
| `feature/*` | 功能开发 | 隔离实验，完成合并后删除 |

- 每次发布打语义化版本 tag（v1.0.0）
- 提交信息遵循 Conventional Commits

## 四、五大配置管理原则

1. **约定优于配置**：用行业共识替代个体决策，不自创结构
2. **关注点分离**：管理/工程/支撑各归其位，不混杂
3. **可追溯性**：每个决策有迹可循（log、需求跟踪矩阵）
4. **隔离与并行**：分支隔离，验证通过再合并
5. **基线与变更控制**：tag 只读，变更走正式流程

## 五、工程交付链路

```
需求 → 设计 → 编码 → 测试 → 交付
```

| 阶段 | 落点 | 产出 |
|------|------|------|
| 需求 | docs/design | 需求规格、用户故事 |
| 设计 | docs/design | 架构图、接口定义、DB 设计 |
| 编码 | src/ | 源码、配置 |
| 测试 | tests/ | 测试用例、报告 |
| 交付 | CHANGELOG + tag | 发布说明、版本标签 |

## 六、开发纪律（本机环境约束）

- **Windows 中文环境**：bat 脚本全英文注释；中文路径用 PowerShell 调用（详见全局编码矩阵）
- 多步骤命令行 → 一键 `.bat` 脚本（无乱码、exit code 合规）
- 文档与代码同仓版本控制
- 每次变更更新 CHANGELOG
