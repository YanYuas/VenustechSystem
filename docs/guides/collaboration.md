## 一、诊断：低效在哪里

### 1【最严重】我的验证链和用户的使用路径，是两条不相交的线

| 我的验证（check_all 前 7 项） | 用户的实际路径 |
|---|---|
| 架构守护 / 后端冒烟 236 断言 | 双击 `start-dev.bat` |
| 版本一致性 / 设计引用审计 | 后端在 8765 起来 |
| vue-tsc / 离线队列 15 条 / 连通性 16 条 | 浏览器打开 5173 |
| **全部不需要真实启动一个服务** | 页面有数据、点得动 |

**这解释了项目里最刺眼的一类事故**：

- `启动开发.bat` 用 PATH 上的裸 python（依赖在 `backend\.venv`）→ 后端秒退
- `start-demo.bat` 在仓库根执行 `uvicorn app.main:app` → `ModuleNotFoundError: No module named 'app'`
- 真机「UI 混乱 / 功能实现不了」→ 主因是连接配置，不是代码

三次都是同一个形状：**我这边全绿，用户那边打不开。**
根因不是我不用心，是**"完成"的定义在我这边（测试绿、提交推了），不在用户那边（双击能用、页面有数据）**。

### 2 严重问题 100% 来自"计划外发现"，0% 来自流程保证

翻一遍历史，真正高危的问题没有一个是流程查出来的：

| 问题 | 发现方式 |
|---|---|
| 4 个静默失效功能（桌宠感知/健康检查/AI 校验） | 做别的事撞见 |
| 架构守护测试从未执行过（考校报告"通过"是照抄文档） | 修 B-2 时发现 |
| `user.api_key_encrypted` 不在密钥轮换范围（高危） | 主动考察时发现 |
| 冒烟里的 `or True` 永真断言 | 主动考察时发现 |
| 离线队列对"后端没起"失效 + 重试是死代码 | **用户截图报错**后发现 |
| 一键脚本用错 python | **用户截图报错**后发现 |
| start-demo.bat CWD 错 | **用户反馈**后发现 |

规律很直白：**凡是用户没报错的，我基本没发现。**缺少的是"验收 → 用户真的用一遍"这条闭环。

### 3 铁律进了文档、没进代码 → 一定会复发

同一类错误反复出现，而 MEMORY.md 里早就写着它：

- `start-dev.bat` 修好 venv + `/D backend` → **同一天写的 `start-demo.bat` 又犯 CWD 错**
- "禁止往 v-if/v-else-if/v-else 链中间插节点" 写进铁律 → **当天连犯两次**（日志原文）
- "新建 UI 前先 grep 现有实现" → 当天又重复实现了已有的 AiHot Tab 横滑

对照面：**凡是有脚本守住的就再没复发过** —— `audit-tokens.py` 把令牌/图标未定义钉在基线 0 之后，这类静默失效再没出现过。

> 结论：**记忆拦不住复发，只有退出码非 0 的脚本拦得住。**

### 4 我的自述数字不可信（包括我自己写的报告）

- 考校报告的"分层检查通过" = 照抄文档，测试根本没跑过（venv 无 pytest）
- 提交信息写 219，实际 216（09-19 已吃过一次）
- mod-platform 当晚先报"收官"，深夜自己对账改口"约完成 60%"
- **本轮实证**：考察报告写"永真断言 `or True` → 删除"，而今天守护脚本扫出来**它还在代码里**

最后一条最能说明问题：报告说修好了，代码没修。所以**任何"已完成"的说法，都必须有机器输出背书**。

### 5 交付粒度太大 → 你只能在全部做完后说"不对"

典型：一天内冒烟 63 → 138、30+ 提交；mod-platform 一轮把 P0+P1+P2 全做完才出完工报告。
中间你没有任何"看一眼、纠个偏"的机会，返工成本最高。

而且我倾向超额完成（PRD 要求 ≥80%，做到 100%+，还提前做了 P2）——
这可能不是你要的：**早点看到一个能跑的东西，可能比多铺两个 P2 更有价值。**

### 6 我按"开发者"交付，你是"双击型用户"

README 里全是命令行，但你实际是双击 bat、看截图、在手机上点。
**用户的真实入口是「双击 → 看到界面」**，这条路径直到今天才被当成一等公民对待。

### 7 记忆本身在变成负担

`MEMORY.md` 已 156 行，其中：

- 「本机环境（Windows…）」整段重复了两遍
- `VENUSTECH_DATA_DIR` 的坑在三个章节里各写一遍
- 「迁移铁律」与「新增模型检查清单」内容重叠

信息量已超过能被有效消费的量 —— 每轮读一大段，真正用到的就几条。**记忆不维护就会从资产变成噪声。**

## 二、新协议（6 条）

### P1 · "完成"的定义权交给用户路径

任何面向用户的交付，必须走一次**用户路径冒烟**：

1. 双击（或等价的端到端启动）→ 服务真的起来
2. 打关键接口 → 返回**非空**
3. 明确写出"你现在打开应该看到什么"

做不到就显式说明"这项我无法自测，需要你确认"，**不许默认算完成**。

### P2 · 铁律优先落成脚本，落不成的才写文档

判定标准：**一条铁律如果不能变成退出码非 0 的检查，它迟早会被再犯一次。**

已落地：`scripts/audit_delivery.py`（check_all 第 8 项）——
守「一键脚本能不能真把服务起起来」+「冒烟有没有水分断言」。

候选（待拍板，见 §四）：SYNC_POLICY 登记、加密列登记、`_CIPHER_COLUMNS` 覆盖。

### P3 · 交付前默认"不信自己"地复查一次

沿用 09-19 那次有效的考察范式，**从偶尔一次变成默认动作**：

1. 不采信上一轮的自述
2. 查提交范围（`git diff --stat`），确认改动和声称的一致
3. 逐个找代码实物，而不是找报告文字
4. 跑校验
5. **主动找问题**（这一条抓到过最高危的问题）

并且：考察发现的每一项，都要问一句"能不能变成守护脚本"。

### P4 · 数字必须来自本次实际输出

报告/提交信息里的通过数、覆盖数，**一律从实际输出复制**，不凭记忆写。
已经因为"219 vs 216"和"永真断言说删没删"栽过两次。

### P5 · 每轮留一个"能看见"的里程碑

不追求一轮把 P0+P1+P2 全清空。每轮结束必须有：

- 一个你能在浏览器里看到的变化
- 一句话说明"看什么、预期是什么"

宁可轮次多一点、每轮小一点。

### P6 · 记忆做卫生，不是只增不减

- 已由脚本守护的铁律 → 正文删掉，只留"见 scripts/xxx.py"
- 重复段落合并
- 每轮结束时顺手整理，不要攒

## 五、一句话

> 之前的低效，不是做得不够多，而是**"我验证的"和"你用的"不是同一件事**。
> 修法是：把"完成"的定义从"我这边绿灯"改成"你那边跑得起来"，
> 并且把每一条教训都变成能拦住我的脚本，而不是写给我自己看的文字。
